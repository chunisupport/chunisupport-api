実施日 2026-10-16 ／ 対象コミット 83ec533（develop 相当） ／ 方式: ソースコード静的レビュー + govulncheck

結論

重大（Critical / High）な脆弱性は見つかりませんでした。認証・認可、非公開ユーザーの閲覧制御、SQL インジェクション対策、APIトークンとデータ移行ファイルの暗号処理は、いずれも丁寧に実装されています。

指摘は主に未認証で使える一時保存API と IP 単位のレート制限に集中しています。少ない送信元から一時保存の全体容量を埋められる問題（M1）と、IPv6 でレート制限を回避できる問題（M2）は、早めの対応を推奨します。

指摘の詳細

M1

一時保存APIの全体容量を少数のIPで枯渇させられる

Medium
箇所
internal/infra/repository/temporary_player_data_repository_impl.go Create、internal/info/info.go（TempData*）
内容
POST /internal/player-data/temp は認証不要です。保持量は展開後のバイト数で数えられ、上限は全体で既定 64MB、1件あたり 5MiB、1IPあたり 3件です。gzip 500KiB 以下で 5MiB に展開されるJSONは容易に作れるため、約13件、つまり5つ程度のIP（IPv6 なら1台の端末で足ります。M2参照）から送るだけで全体容量が埋まります。
影響
TTLの5分間、全利用者のブックマークレット経由のアップロードが 503 になります。5分ごとに送り直せば、この状態を続けられます。
対策案
  • IP単位の件数制限に加えて、IP単位の合計バイト数にも上限を設ける（例: 全体の数%）。
  • IPv6 は /64 単位でまとめて数える（M2 の対策と共通化）。
  • 展開後の上限（5MiB）を実データの最大サイズに合わせて引き下げる、または圧縮後のまま保持して確定時に展開する。
M2

IPベースのレート制限がIPv6の1アドレス単位

Medium
箇所
internal/app/middleware/rate_limit_middleware.go の IPRateLimitMiddleware / AnonymousIPRateLimitMiddleware、ip_username_rate_limit_middleware.go
内容
識別子に c.RealIP() の文字列をそのまま使っています。一般的なIPv6回線では利用者1人に /64（264 個）以上のアドレスが割り当てられるため、送信元アドレスを変えるだけで制限を受けません。
影響
ログイン（10回/分）・新規登録（5回/時）・一時保存（30回/分, 3件/IP）・未認証の公開API（60回/分）の制限を回避できます。ログインと新規登録は Turnstile があるため影響は限定的ですが、一時保存（M1）と公開APIの負荷対策は実質的に効きません。
対策案
IPv6 アドレスは netip.Prefix で /64（または /56）に丸めてからキーにする共通関数を用意し、全てのIPベース制限で使う。
M3

一時保存トークンを他人に確定させられる

Medium（条件付き）
箇所
internal/usecase/temporary_player_data_usecase_impl.go Commit、POST /internal/player-data/commit
内容
一時保存データは誰でも任意の内容で作成でき、uploadToken を知っている認証済みユーザーなら誰でも自分のアカウントへ確定できます。アップロードした人と確定する人の結び付きは確認していません。
成立条件
フロントエンドが URL などで受け取った uploadToken を、内容の確認なしに自動で commit する場合に成立します。攻撃者が偽造スコアで作ったトークン付きリンクを踏ませると、被害者のプレイヤーデータ・スコア履歴が攻撃者の用意した内容で上書きされます（ログインCSRFに近い型）。
対策案
  • フロントで確定前にプレイヤー名・件数などの要約を表示し、明示的な操作で確定させる（最小対応）。
  • サーバー側では、確定時のIPと保存時のIP（entry.IPAddress、既に保持済み）が異なる場合に拒否する、または既存プレイヤーとプレイヤー名が異なる場合は警告を返す。
L1

読み取り系GETはトークンの失効を確認しない

Low
箇所
internal/app/router.go の firebaseAuthReadOptimized 適用グループ（/internal/me GET、/friends GET、/friend-rankings、/friend-comparisons、公開系のオプショナル認証）
内容
VerifyIDToken（失効確認なし）を使っているため、パスワード変更・セッション失効・アカウント無効化の後も、IDトークンの有効期限（最大1時間）までは閲覧できます。フレンド比較など非公開データも対象です。
評価
応答速度とのトレードオフとして意図された設計で、書き込み系は全て厳密検証です。トークン漏えい時の影響が「最大1時間の閲覧」に限られる点を許容できるか確認してください。必要なら非公開データを返すフレンド比較系だけ厳密検証に切り替えられます。
L2

クライアントIP判定がプロキシ設定に強く依存する

Low（運用確認）
箇所
internal/app/router.go configureIPExtractor、docs/configuration.md
内容
コード自体は正しく、信頼するCIDRからの X-Forwarded-For だけを使います。ただし Cloudflare → nginx → API の構成で nginx が CF のIPを実IPへ置き換えていない場合、全利用者が Cloudflare エッジのIPとして扱われ、レート制限を利用者全体で共有してしまいます（正規利用者が429になる）。逆に nginx がクライアント由来の X-Forwarded-For をそのまま引き継ぐと、IPを偽装できます。
対策案
本番の nginx で set_real_ip_from（Cloudflare のIP範囲）と real_ip_header CF-Connecting-IP を設定し、proxy_set_header X-Forwarded-For $remote_addr で上書きしていることを確認する。
L3

DBの数値IDがAPIの id として露出している

Low
箇所
internal/app/handler/api_internal/api_token_handler.go:23（uint64）、internal/dto/api_internal/goal_dto.go:18、goal_group_dto.go:12
内容
APIトークン・目標・目標グループのAUTO_INCREMENT値が id として返ります。所有者スコープ（WHERE id = ? AND user_id = ?）は徹底されているためIDORにはなりませんが、サービス全体の作成件数や作成ペースが推測でき、AGENTS.md の「数値IDの露出禁止」にも反します。
対策案
他リソースと同様に display_id（ランダムな公開ID）を導入し、APIではそちらを id として扱う。
L4

レート制限ストアの件数に上限がない

Low
箇所
internal/app/middleware/rate_limit_middleware.go FixedWindowStore
内容
エントリは時間窓の2倍経過後に削除されますが、窓の間は識別子ごとに無制限に増えます。M2 のようにIPv6アドレスを変え続けると、1窓の間にメモリ使用量を増やせます（/badges はIP×ユーザー名のキーなので特に増えやすい）。
対策案
M2 の /64 丸めで大半は解消します。加えてエントリ数の上限を設けると確実です。
I1

新規登録でメール確認済みかを見ていない

Info
箇所
internal/usecase/signup_usecase.go
内容
有効なFirebaseトークンであれば、email_verified やサインインプロバイダを問わず登録できます。Firebase 側でメール/パスワードや匿名認証を有効にしている場合、使い捨てアカウントを量産できます（Turnstile と 5回/時/IP の制限はあります）。Firebase コンソールで有効なプロバイダを確認してください。

Info
箇所
internal/infra/turnstile/verifier.go
内容
success だけを見ています。同じサイトキーを複数ホストやフォームで使う場合、別の場所で取得したトークンを流用できます。レスポンスの hostname と action（login / signup）を照合すると防げます。
I3

楽曲バッチのダウンロードで応答サイズの上限がない

Info
箇所
internal/infra/songbatch/datasource/downloader.go:140（io.ReadAll(resp.Body)）
内容
取得先は設定済みの信頼できるURLで、起動できるのはADMINだけです。取得先が侵害された場合の備えとして io.LimitReader を付けておくと安全です。

確認して問題がなかった項目

  • ✓
    SQLインジェクション: 動的SQLは全てプレースホルダ。fmt.Sprintf で埋め込むのはコード内の定数・列名・プレースホルダ列だけ。LIKE検索は % _ \ をエスケープ済み。
  • ✓
    ルート単位の認可: 管理系（/internal/admin、/honors、ユーザー削除・権限変更）は厳密認証 + ADMIN、楽曲編集は EDITOR。rejectUnmatchedRoute で未登録パスが認証前に404になる。
  • ✓
    非公開ユーザー: canAccessPrivateUser に集約され、プロフィール・レコード・履歴・コース・ロック/お気に入り曲・バッジ・chunirec互換・v1 の全経路で適用。非公開は404で返し、存在を隠している。
  • ✓
    フレンド: 比較・ランキングはSQLで双方向の承認済み関係を要求。承認は相手からの保留中申請がある場合に限られる。
  • ✓
    IDOR: 目標・目標グループ・レコードフィルタ・APIトークン・ロック/お気に入り曲の更新・削除は全て user_id / player_id で絞り込み。プレイヤーデータはユーザー単位で紐付くため他人のプレイヤーを乗っ取れない。
  • ✓
    重要操作の再認証: ユーザー名変更・退会は X-Reauth-Token の失効確認付き検証、auth_time 5分以内、UID一致を要求。管理者の自己降格・自己削除は禁止。
  • ✓
    APIトークン: 32バイトの暗号論的乱数、SHA-256で保存、平文は発行時のみ。書き込み権限トークンの発行と利用の両方でEDITOR以上を要求。クエリ文字列でのトークン受け取りはない。
  • ✓
    データ移行ファイル: HMAC-SHA256（秘密鍵32バイト以上）を hmac.Equal で比較してから展開。厳密なJSON・Base64検証、gzip爆弾対策の展開上限あり。
  • ✓
    入力サイズ: 全体5MiB（移行のみ32MiB）のボディ上限、gzip展開時の LimitReader、Echo 既定の ReadTimeout 30秒。
  • ✓
    エラー応答とログ: 内部エラーの詳細はクライアントに返さない。ログは改行を除去。Google API キー入りURLはエラー文から除いている。
  • ✓
    CORS: 許可オリジンは明示リスト。* と credentials の併用は起動時に拒否。外部オリジンは一時保存・死活・状態取得の3パスだけに限定。
  • ✓
    秘密情報: 鍵・認証情報は環境変数と .config/ で管理し、.gitignore 済み。リポジトリ内に秘密情報のファイルは見当たらない。APIは 127.0.0.1 でのみ待ち受け。
  • ✓
    依存ライブラリ: govulncheck ./... の結果、コードから到達可能な既知脆弱性は0件（依存モジュールに1件あるが未使用の経路）。

範囲と制約

対象は本リポジトリのGoコード（cmd/・internal/）と設定ドキュメントです。フロントエンド、nginx・Cloudflare・Firebase の本番設定、DBの権限設定は確認していません（M3・L2・I1 はそれらの確認が前提）。動的テストやペネトレーションテストは行っていません。_report/ 配下の資料は仕様の根拠として扱っていません。
