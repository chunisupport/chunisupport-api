# ユーザーデータ移行機能 実装計画書

## 1. 目的

内部IDが異なるChuniSupportサーバー間で、ユーザー自身がプレイヤーデータを移行できるようにする。

各サーバーは同じアプリケーションコードと同等のマスターデータを使用するが、楽曲、譜面、コース、称号、各種マスターのDB内部IDは一致しない。そのため、移行ファイルにはDB内部IDを含めず、`official_idx`、難易度名、マスター名などのサーバー間で一致する値を保存する。

本機能は次の運用を前提とする。

- 移行ファイルを相互利用するサーバーは同じHMAC秘密鍵を安全に共有する
- 移行先では、プレイヤーデータ、目標、保存済みフィルタが未登録のアカウントだけがインポートできる
- エクスポート、検証、インポートAPIは常時利用できる
- サーバー間の直接通信は行わず、ユーザーが署名付き移行ファイルをダウンロードしてアップロードする

---
## 2. 採用方針

### 2.1 全体方針

以下を採用する。

1. バージョン付きの署名済み移行ファイルを使用する
2. 移行ファイルのペイロードはgzip圧縮する
3. 相互移行するサーバーで共有する秘密鍵を使い、HMAC-SHA256で署名する
4. 移行先の既存データとはマージしない
5. 解決不能なマスター参照が1件でもあれば、全体をインポートしない
6. インポートは単一トランザクションで実行する
7. レーティングなどの派生値は、移行先のマスターデータを使って再計算する
8. 移行元データはインポート成功後も自動削除しない

### 2.2 この対応で行わないこと

- 任意の外部サーバーから公開鍵を取得する仕組み
- `.well-known`エンドポイント
- サーバー間通信によるデータ取得
- 移行コードやワンタイムトークンの発行
- 移行ファイルの暗号化
- 移行ファイルの有効期限
- 同一ファイルが別の空アカウントで使われることの全体的な追跡
- 既存プレイヤーデータ、目標、フィルタとの統合
- 部分インポート、未解決データのスキップ
- 認証情報、権限、フレンド関係の移行

HMACはファイルの改変や破損を検出するために使用する。ペイロードは暗号化されないため、移行ファイルにはプレイ履歴を含む個人データが平文相当で格納されることを画面上で案内する。

---

## 3. ユーザー操作フロー

1. ユーザーが移行元サーバーへログインする
2. 移行画面から移行ファイルをダウンロードする
3. ユーザーが移行先サーバーで空のアカウントを作成し、ログインする
4. 移行先の画面で移行ファイルを選択する
5. 移行先APIがファイルを検証し、データ件数とインポート可否を返す
6. ユーザーがプレビュー内容を確認してインポートを確定する
7. 移行先APIがファイルを再検証し、全データを1トランザクションで保存する
8. フロントエンドがプロフィール、レコード、履歴、目標などのキャッシュを破棄して再取得する

プレビュー結果をサーバー側へ一時保存しない。確定時には同じファイルを再送し、署名、内容、マスター参照、移行先の空状態をすべて再検証する。

---
## 4. API設計

すべてFirebase Bearer認証を必須とし、認証済みユーザー本人だけを対象にする。3つの操作ルートは常時登録する。

### 4.1 エクスポート

```text
POST /internal/me/data-transfer/export
```

- 認証ユーザーにプレイヤーが紐付いていない場合は拒否する
- 成功時は署名済みJSONファイルを返す
- `Content-Type: application/json`
- `Content-Disposition: attachment; filename="chunisupport-transfer.json"`
- サーバー上にファイルを保存しない

### 4.2 インポート検証

```text
POST /internal/me/data-transfer/validate
```

- リクエストボディはエクスポートしたJSONファイルの内容そのものとする
- ファイルを永続化せず、署名、形式、データ、マスター参照、移行先の空状態を検証する

レスポンス例:

```json
{
  "importable": true,
  "player_name": "TEST PLAYER",
  "counts": {
    "records": 1800,
    "record_histories": 4200,
    "worldsend_records": 40,
    "worldsend_record_histories": 80,
    "metric_histories": 20,
    "course_records": 8,
    "honors": 3,
    "favorite_songs": 25,
    "locked_songs": 12,
    "goal_groups": 3,
    "goals": 15,
    "record_filters": 4
  },
  "blockers": [],
  "unresolved_references": [],
  "unresolved_reference_count": 0
}
```

ファイル自体が不正な場合は4xxを返す。形式は正しいが移行先が空でない、または参照先マスターを解決できない場合は、`200 OK`かつ`importable=false`として阻害理由を返す。

`unresolved_references`はレスポンス肥大化を防ぐため先頭100件までとし、別途総件数を返す。

### 4.3 インポート確定

```text
POST /internal/me/data-transfer/import
```

- リクエストボディは検証時と同じ移行ファイルとする
- 成功時は`200 OK`で新しい`player_id`と保存件数を返す
- インポート直前に全検証を再実行する
- 移行先が空でなければ`409 Conflict`を返す
- 参照解決や保存に失敗した場合はロールバックする

### 4.4 レート制限

エクスポート、検証、確定にはFirebaseユーザー単位の専用レート制限を設定する。1分あたり5回とし、3つの操作で同じカウンターを共有する。

---
## 5. 秘密鍵設定

settings JSONにデータ移行用の設定節は追加しない。APIサーバーでは次の環境変数を必須とする。

```text
DATA_TRANSFER_HMAC_SECRET=<Base64で表現した32バイト以上のランダム値>
```

設定検証規則:

- 秘密鍵はBase64デコード後32バイト以上を必須にする
- 移行ファイルを相互利用するサーバーには同じ秘密鍵を設定する
- 秘密鍵や署名値をログへ出力しない
- バッチコマンドでは秘密鍵を要求しない

`router.go`ではエクスポート、検証、インポートの3ルートを常時登録する。

## 6. 移行ファイル形式

### 6.1 エンベロープ

JSONの再シリアライズ差によって署名検証が不安定にならないよう、JWSに近い3要素の形式を使用する。

```json
{
  "protected": "<ヘッダーJSONをBase64URL化した文字列>",
  "payload": "<ペイロードJSONをgzip圧縮してBase64URL化した文字列>",
  "signature": "<署名をBase64URL化した文字列>"
}
```

Base64URLはパディングなし形式を使用する。

署名対象は、ファイル内に記録された文字列をそのまま連結した次のASCIIバイト列とする。

```text
protected + "." + payload
```

署名値は以下で生成する。

```text
HMAC-SHA256(DATA_TRANSFER_HMAC_SECRET, signing_input)
```

インポート側は`hmac.Equal`を使って定数時間比較する。

### 6.2 署名対象ヘッダー

```json
{
  "format": "chunisupport-user-transfer",
  "schema_version": 1
}
```

- 未知の`schema_version`は拒否する
- 未知フィールドは拒否し、バージョンごとのデコーダーで明示的に扱う
- サーバーID、移行ID、エクスポート日時は持たない
### 6.3 サイズ制限

履歴件数が多いユーザーでも移行できるよう、通常APIの5MiB制限とは分けて以下を設ける。

- エンベロープ全体: 32MiB
- Base64URLデコード後のgzipデータ: 24MiB
- gzip解凍後JSON: 128MiB

実装では`io.LimitReader`を解凍前後に適用し、gzip爆弾を防ぐ。現在のグローバルBodyLimitでは32MiBを受け付けられないため、データ移行ルートだけ専用上限を適用できるようBodyLimitの構成を変更し、その他のルートは5MiBを維持する。

## 7. ペイロード仕様

ペイロードには移行元の`user_id`、`player_id`、楽曲ID、譜面ID、コースID、称号ID、各種マスターIDを含めない。時刻はAPI出力タイムゾーン設定に依存させず、UTCで保存する。

概略形は以下とする。

```json
{
  "player": {},
  "records": [],
  "record_histories": [],
  "worldsend_records": [],
  "worldsend_record_histories": [],
  "metric_histories": [],
  "course_records": [],
  "honors": [],
  "favorite_songs": [],
  "locked_songs": [],
  "goals": {
    "groups": [],
    "ungrouped": []
  },
  "record_filters": []
}
```

### 7.1 プレイヤー

保存する値:

- プレイヤー名
- プレイヤーレベル
- 公式RATING
- 公式OVER POWER
- クラスエンブレム名
- クラスエンブレムベース名
- 最終プレイ日時
- データ取得日時
- プレイヤー作成日時

保存しない派生値:

- `calculated_player_rating`
- `new_average_rating`
- `best_average_rating`
- `overpower_value`
- OVER POWER割合

`players.updated_at`と`users.updated_at`はインポート日時に更新する。

### 7.2 通常譜面レコード

各レコードに以下を保存する。

- 楽曲`official_idx`（文字列として保持し、数値化しない）
- 難易度名（`BASIC`、`ADVANCED`、`EXPERT`、`MASTER`、`ULTIMA`）
- スコア
- クリアランプ名
- コンボランプ名
- フルチェイン名
- スロット名
- `slot_order`
- 更新日時

移行先では`official_idx + 難易度名`を使って`chart_id`を解決する。

### 7.3 通常譜面スコア履歴

各履歴に以下を保存する。

- 楽曲`official_idx`
- 難易度名
- スコア
- クリアランプ名
- コンボランプ名
- フルチェイン名
- 更新日時

現在レコードと履歴テーブルの行を分けて保持する。履歴は1譜面あたり既存上限の50件以内であることを検証する。

### 7.4 WORLD'S ENDレコードと履歴

- 楽曲`official_idx`
- スコア
- クリアランプ名
- コンボランプ名
- フルチェイン名
- 更新日時

移行先では`official_idx`からWORLD'S END譜面を解決する。

### 7.5 公式指標履歴

`player_metric_histories`の以下を保存する。

- 公式RATING
- 公式OVER POWER
- データ取得日時

同一取得日時の重複と、現在のプレイヤー指標との時系列矛盾を検証する。

### 7.6 コース記録

- コース`official_idx`
- スコア
- クリア状態
- コンボランプ名
- 更新日時

コースの`display_id`と内部IDは使用しない。

### 7.7 称号

- スロット番号
- 称号画像URL
- 称号名
- 称号タイプ名
- 装着日時

移行先での解決優先順位は以下とする。

1. 画像URLがある場合は画像URL
2. 画像URLがない場合は`称号名 + 称号タイプ名`

移行先マスターに存在しない称号をインポート処理から新規作成しない。

### 7.8 お気に入り楽曲

- 楽曲`official_idx`
- お気に入り登録日時

### 7.9 未解禁楽曲

- 楽曲`official_idx`
- `is_ultima`

### 7.10 目標と目標グループ

目標グループを入れ子にし、移行元の数値IDを参照しない。

```json
{
  "goals": {
    "groups": [
      {
        "name": "今月",
        "sort_order": 1,
        "created_at": "2026-08-01T00:00:00Z",
        "goals": []
      }
    ],
    "ungrouped": []
  }
}
```

各目標には以下を保存する。

- タイトル
- achievement typeのコード
- `achievement_params`
- 外向き表現へ変換した`attributes`
- `invert_value`
- `invert_percentage`
- グループ内表示順
- 作成日時

`attributes`は次の項目だけ内部IDから外向き値へ変換し、その他のキーは既存JSON構造を保つ。

- `diff`: 難易度名
- `genre`: ジャンル名
- `ver`: バージョン名

インポート時に名称から移行先IDへ戻し、既存のGoal入力検証と動的上限検証を再利用する。目標IDと目標グループIDは移行先で新規採番する。

### 7.11 保存済みフィルタ

- 保存名
- `filter_type`
- `schema_version`
- `filter` JSONオブジェクト
- 作成日時
- 更新日時

フィルタ本文は現行APIと同様にバックエンドで意味解釈せず、そのまま移行する。フィルタIDは移行先で新しいUUIDを生成する。

現行フロントエンドの通常フィルタとWORLD'S ENDフィルタは、難易度を文字列enum、ジャンルとバージョンを名称文字列として保存しており、サーバー内部IDを含まない。そのため、同じフロントエンド形式を使用する対応サーバー間では本文を変換せず移行できる。実装時には現行および移行対象となる旧`schema_version`の型をテストデータで固定し、将来のスキーマで内部ID参照を追加する場合は移行ファイルのバージョンを更新する。

## 8. 移行しないデータ

| データ | 理由 |
|---|---|
| Firebase UID | 移行先アカウントの認証情報を維持するため |
| ユーザー名 | 移行先で作成したアカウント名を維持するため |
| アカウントタイプ | 移行先サーバーの権限設定を維持するため |
| 公開・非公開設定 | 移行先アカウントの設定を維持するため |
| suspicious状態 | 移行先サーバーの管理情報であるため |
| APIトークン | 認証秘密情報を持ち出さないため |
| フレンド関係 | 相手ユーザーIDがサーバー固有であるため |
| `player_latest_updates` | 通常データ登録結果のキャッシュであり、移行後の実データから復元する対象ではないため |
| 一時プレイヤーデータ | インメモリの一時処理データであるため |
| 譜面統計・ランキング集計 | ユーザー個人の正規データではなく、サーバー全体で再集計するため |

インポート直後の`GET /internal/me/player-data/latest-update`は、次の通常データ登録まで`204 No Content`を返してよい。

## 9. マスター参照の変換規則

| 移行対象 | ファイル内のキー | 移行先で解決する値 |
|---|---|---|
| 通常譜面 | `song_official_idx + difficulty` | `chart_id` |
| WORLD'S END譜面 | `song_official_idx` | `worldsend_chart_id` |
| お気に入り・未解禁楽曲 | `song_official_idx` | `song_id` |
| コース | `course_official_idx` | `course_id` |
| 難易度 | 大文字の難易度名 | `difficulty_id` |
| クリアランプ | マスター名 | `clear_lamp_id` |
| コンボランプ | マスター名 | `combo_lamp_id` |
| フルチェイン | マスター名 | `full_chain_id` |
| スロット | マスター名 | `slot_id` |
| クラスエンブレム | マスター名 | `class_emblem_id` |
| クラスエンブレムベース | マスター名 | `class_emblem_base_id` |
| 称号 | 画像URL、または名称とタイプ名 | `honor_id` |
| achievement type | コード | `achievement_type_id` |
| 目標ジャンル条件 | ジャンル名 | `genre_id` |
| 目標バージョン条件 | バージョン名 | `version_id` |

照合では論理削除済みの楽曲・コースも対象に含める。移行元に残っている履歴を欠落させないためであり、公開APIでの表示可否とは分離する。

照合に必要な値をペイロード全体から先に収集し、種類ごとに一括取得する。レコードや履歴1件ごとの検索は行わず、N+1を発生させない。

## 10. 移行先の空状態

次をすべて満たす場合だけインポート可能とする。

1. 対象`users`行が存在する
2. `users.player_id IS NULL`
3. `players.user_id = 対象ユーザーID`の行が存在しない
4. `goals`が0件
5. `goal_groups`が0件
6. `record_filters`が0件

プレイヤーが存在しなければ、通常レコード、履歴、称号、お気に入り、未解禁曲、コース記録、公式指標履歴は外部キー上存在できない。そのため、それらを空判定で個別に数える必要はない。

以下は存在していてもインポートを許可する。

- Firebase UID
- APIトークン
- フレンド申請・フレンド関係
- 移行先の公開・非公開設定

検証APIでは読み取りだけで判定する。確定時はトランザクション内で対象`users`行を`FOR UPDATE`ロックし、同じ条件を再判定する。

専用の移行済みテーブルは追加しない。インポート後はプレイヤーが紐付くため、同じアカウントへの再実行は空状態判定で拒否される。プレイヤーデータを削除して再び完全な空状態に戻した場合は、移行ルートが有効な期間中に再インポートできる仕様とする。

## 11. エクスポート処理

1. 設定と認証ユーザーを確認する
2. 認証ユーザーにプレイヤーが紐付いていることを確認する
3. REPEATABLE READの読み取り専用トランザクションでユーザーデータの整合したスナップショットを取得する
4. 固定本数のJOIN／一括クエリで、DB内部IDを外向きキーへ変換する
5. 目標JSON内の`diff`、`genre`、`ver`を外向き値へ変換する
6. 配列順と時刻表現を正規化する
7. ドメイン上の不整合がないことを検証する
8. ペイロードJSONをgzip圧縮する
9. ヘッダーとペイロードにHMAC署名する
10. 添付ファイルとしてレスポンスする

スナップショット取得中に不正な外部キー、未知のマスターID、重複キーなどを検出した場合は、欠落データを含むファイルを発行せずエラーにする。

通常の履歴取得APIは現在値と履歴テーブルを結合して返すため、エクスポートには使用しない。移行専用Queryで履歴テーブルだけを取得し、現在レコードと二重に保存されることを防ぐ。また、履歴テーブルのランプ参照に外部キーがないことを考慮し、マスターとのJOINで行を黙って欠落させず、LEFT JOIN後の未解決参照をエラーにする。

## 12. 検証・インポート処理

### 12.1 共通事前検証

検証APIと確定APIは同じ検証関数を使用する。

1. エンベロープサイズを検証する
2. JSONを未知フィールド拒否でデコードする
3. `protected`、`payload`、`signature`をBase64URLデコードする
4. HMAC署名を検証する
5. ヘッダー形式、スキーマバージョン、許可された移行元を検証する
6. gzipを解凍上限付きで展開する
7. ペイロードを未知フィールド拒否でデコードする
8. 必須値、値域、件数、重複、時系列、表示順を検証する
9. 参照キーを種類ごとに一括解決する
10. 目標の外向き属性を移行先IDへ変換し、既存バリデーションを通す
11. 移行先の空状態を確認する

署名検証をgzip展開より先に実行し、改変された大容量データを展開しない。

### 12.2 派生値の再計算

保存前に、解決済みの譜面定数、スコア、スロット、未解禁状態を使って以下を再計算する。

- 計算レーティング
- Best枠平均
- New枠平均
- OVER POWER値

既存の`service.AggregateOfficialRating`、`service.CalcOverpowerSummary`などを再利用する。通常データ登録と移行で計算式を複製せず、共通の計算関数へ抽出する。

公式RATING、公式OVER POWER、公式指標履歴はゲームから取得した値として移行元の値を維持する。

グローバル譜面統計とランキングはインポート処理内で更新せず、既存の統計集計処理が次に実行された時点で反映する。

### 12.3 トランザクション内保存順

1. `users`行を`FOR UPDATE`でロックする
2. 空状態を再確認する
3. `players`を作成して新しい`player_id`を取得する
4. 通常レコードを一括挿入する
5. WORLD'S ENDレコードを一括挿入する
6. 通常／WORLD'S ENDスコア履歴を一括挿入する
7. 公式指標履歴を一括挿入する
8. コース記録を一括挿入する
9. 称号、お気に入り、未解禁楽曲を一括挿入する
10. 目標グループを表示順に作成し、新しいグループIDを取得する
11. 目標を対応する新グループIDで一括挿入する
12. 保存済みフィルタに新しいUUIDを割り当てて挿入する
13. `users.player_id`を新しいプレイヤーへ紐付ける
14. `users.updated_at`を更新する
15. 件数を照合してコミットする

一括挿入は`info.BulkInsertChunkSize`を上限に分割する。1件でも失敗した場合は全処理をロールバックする。

## 13. ドメイン検証

最低限、以下を検証する。

- プレイヤー名、レベル、公式指標が既存ドメイン制約内である
- 通常譜面キー、WORLD'S ENDキー、コースキーが重複していない
- 各履歴の`譜面キー + updated_at`が重複していない
- DBの時刻精度へ正規化した後にも履歴キーが重複しない
- スコア、コーススコア、ランプ、スロット、`slot_order`が有効である
- Best、New、候補枠の件数と`slot_order`が既存ルールに一致する
- 公式指標履歴が時系列順で、同一日時に異なる値を持たない
- 称号スロットが1〜3で重複しない
- お気に入りが既存上限以内である
- 目標が100件以内、目標グループが20件以内である
- 目標／グループの表示順がグループごとに1から連続している
- 目標グループ名が重複していない
- 保存済みフィルタが100件以内で、各フィルタが既存の8KiB制限を満たす
- すべての配列が`null`ではなく空配列または要素配列である

署名済みファイルであっても、ドメインバリデーションは省略しない。署名は内容の妥当性ではなく、発行後に内容が変わっていないことだけを保証する。

## 15. エラー設計

追加するUsecaseエラーとAPIエラーコードの候補:

| エラーコード | HTTP | 条件 |
|---|---:|---|
| `data_transfer_player_not_found` | 400 | エクスポート元にプレイヤーがない |
| `data_transfer_invalid_file` | 400 | JSON、Base64URL、gzip、必須項目が不正 |
| `data_transfer_invalid_signature` | 400 | HMACが一致しない |
| `data_transfer_unsupported_schema` | 400 | 未対応のファイル形式またはバージョン |
| `data_transfer_invalid_data` | 400 | 値域、重複、順序、件数などが不正 |
| `data_transfer_unresolved_reference` | 400 | 移行先マスターへ解決できない |
| `data_transfer_destination_not_empty` | 409 | 移行先に対象データがある |
| `payload_too_large` | 413 | 圧縮前後いずれかの上限超過 |
| `internal_error` | 500 | DB、圧縮、予期しない内部不整合 |

署名値、秘密鍵、ペイロード本体、Firebase UIDをエラー本文やログへ含めない。

## 17. テスト方針

TDDで、失敗するテストを先に追加してから実装する。新規テストでは`testify/assert`と`testify/require`を使用する。

### 17.1 コーデック単体テスト

- エクスポートして同じ秘密鍵で復号・検証できる
- ヘッダー、ペイロード、署名の各改変を拒否する
- 異なる秘密鍵を拒否する
- 未対応バージョンを拒否する
- 不正なBase64URL、gzip、JSON、未知フィールドを拒否する
- 空ペイロードを拒否する
- 圧縮前後の上限超過を拒否する
- gzip爆弾相当の入力を上限で停止する
- HMAC比較に`hmac.Equal`を使用している
- 保護ヘッダーに`format`と`schema_version`以外が入らない

### 17.2 ドメイン・Usecaseテスト

- すべての内部IDが外向きキーへ変換される
- 目標の`diff`、`genre`、`ver`を往復変換できる
- 保存済みフィルタ本文が変化しない
- 各種重複、件数超過、順序不正、値域不正を拒否する
- 移行先が空の場合だけ`importable=true`になる
- APIトークンやフレンド関係だけが存在する場合は許可する
- 検証後に移行先状態が変わった場合、確定処理で拒否する
- 同じ空アカウントへの同時インポートは片方だけが成功する
- 派生レーティングとOVER POWERを移行先マスターから再計算する
- 途中エラーで一部データが残らない

### 17.3 Repositoryテスト

- エクスポートが論理削除済み楽曲・コースを含める
- 固定本数の一括クエリで全セクションを取得する
- 移行先内部IDへ正しく解決する
- グループとプレイヤーの新IDが所有データへ正しく反映される
- チャンク境界の前後で欠落・重複がない
- `users.player_id`の紐付けまで原子的に実行される
- SQLエラー、外部キーエラー、件数不一致でロールバックする

### 17.4 Handler・Router・Configテスト

- 3つの操作ルートが常時登録され、Firebase認証を必須とする
- 固定のContent-DispositionとContent-Typeが正しい
- 各Usecaseエラーが想定HTTPステータスへ変換される
- 通常ルートは5MiB、validate/importは32MiBのBodyLimitになる
- 3つの操作がユーザー単位のレート制限カウンターを共有する
- APIサーバーは未設定、短い鍵、不正なBase64鍵で起動に失敗する
- settings JSONに`data_transfer`節を必要としない

### 17.5 サーバー間往復テスト

同じマスター値に異なる内部IDを割り当てた移行元DBと移行先DBを用意し、全種類のユーザーデータを移行した後、意味上のデータが一致することを確認する。通常／WORLD'S ENDの現在記録と履歴、公式指標履歴、コース、称号、お気に入り、未解禁、目標、保存済みフィルタ、論理削除済みマスターを含める。

## 18. 実装順序

1. 移行ファイルv1の型とドメイン検証を実装する
2. HMAC／gzipコーデックを実装する
3. 環境変数からの秘密鍵読み込みを実装する
4. 外向き参照キーを返すエクスポート処理を実装する
5. 一括マスター解決と検証処理を実装する
6. 原子的なインポート処理を実装する
7. Handler、常時ルート、専用BodyLimit、レート制限、エラー変換を接続する
8. API、設定、ドメイン仕様の文書を更新する
9. 全テスト、`go vet`、`gofmt -s`、UTF-8検査を実行する

## 20. 配備と運用

相互に移行を許可するサーバーへ同じ実装と同じHMAC秘密鍵を配備する。各サーバーではexport、validate、importを常時利用できる。

動作確認では、一方のサーバーからエクスポートし、内部IDが異なる別サーバーの空アカウントでvalidateとimportを実行する。件数、プレイヤー名、全レコード、履歴、目標、フィルタ、派生値が一致し、その後も通常データ更新が可能であることを確認する。

秘密鍵をローテーションすると旧鍵で署名したファイルは利用できなくなる。ローテーション時は相互移行する全サーバーを同時に更新する。

## 21. 完了条件

- 任意の対応サーバーで自分の署名付き移行ファイルを取得できる
- 空アカウントだけがファイルを検証・インポートできる
- 楽曲・譜面などの内部IDが異なっても、`official_idx`とマスター名で正しく解決できる
- 現在スコア、履歴、公式指標履歴、目標、フィルタを含む対象データが欠落しない
- 認証情報、権限、フレンド関係が移行されない
- 参照不能または不正なデータがある場合、部分保存されない
- 派生レーティングとOVER POWERが移行先マスターから再計算される
- settings JSONに移行設定節がなく、共有HMAC鍵だけで動作する
- サーバーID、移行ID、エクスポート日時をファイル・API・ログに持たない
- `go test ./...`と`go vet ./...`が成功する
