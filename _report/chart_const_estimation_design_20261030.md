# プレイヤーデータによる譜面定数推定 設計案

作成日: 2026-10-30

## 0. 文書の位置付け

本書は、新バージョン稼働直後に、新バージョンをプレイ済みのプレイヤーデータから譜面定数を推定する仕組みの設計案である。未実装であり、仕様の根拠ではない。実装時は正式な仕様を `docs/` へ反映する。

対象は通常譜面（BASIC〜ULTIMA）とし、WORLD'S ENDは対象外とする。

---

## 1. 背景と目的

譜面定数は公式に公開されず、現在はsong-batchが外部の定数表（Googleスプレッドシート）から取り込んでいる。新バージョン稼働直後は次の2種類の譜面で定数が不明または不確かになる。

1. **新曲**: 定数が未確定（`charts.is_const_unknown = 1`）で、暫定値で扱われる。
2. **旧曲の定数変更**: 大型アップデートでは旧曲の一部の定数が変更されるが、どの譜面が変わったかは公表されない。表示レベルが変わった譜面は公式データから分かるが、同じレベル内での変更（例: 14.7 → 14.8）は分からない。

chunisupportには、CHUNITHM-NETから取得した公式レーティング枠・公式レート・公式OVER POWERが集まっている。これを使い、次の2点を目的とする。

- 旧曲の定数変更を早く検知し、変更された譜面と変更方向を示す。
- 新曲を含む各譜面について、データから確定できる定数、または取りうる範囲を示す。

推定結果は管理者が確認するための参考情報とし、`charts.const` を自動で書き換えない。

---

## 2. 前提となる計算式

単曲レーティング・プレイヤーレーティング・OVER POWERの計算式は [rating_calculation.md](../docs/rating_calculation.md) と [overpower_calculation.md](../docs/overpower_calculation.md) に従う。本設計で使う性質は次のとおりである。

- 譜面定数は0.1刻みで、表示レベルから候補が最大5値に絞れる（`14` なら14.0〜14.4、`14+` なら14.5〜14.9）。レベル10未満は一意に決まる。
- スコア900,000以上の単曲レーティングは「譜面定数 + スコアだけで決まる値」で、定数に対する傾きは1である。BBB以下は非線形だが、候補が5値しかないため表で扱える。
- 単曲レーティングは小数第2位で切り捨てる。プレイヤーレーティングは50曲合計の1/50を小数第2位で切り捨てた値が表示される（公式表示は小数2桁）。
- 単曲OPはS以上で0.005刻み、定数に対する傾きは5である。楽曲ごとに最もOPが高い難易度だけを合計する。

以降、譜面定数を10倍した整数を `x`、単曲レーティングを100倍した整数を `r` と書く。

## 3. 推定に使う情報

### 3.1 制約の種類

プレイヤー `p` の1回の登録データから、次の制約が得られる。

| ID | 情報源 | 制約 | 有効性 |
|---|---|---|---|
| C1 | 枠内の並び順（`slot_order`） | 同じ枠で隣り合う譜面 i, i+1 について `r_i ≥ r_{i+1}` | 強い。900,000以上なら定数の差の下限になる。新曲枠の未知数と混ざらない |
| C2 | 枠外の旧曲記録 | ベスト枠が30曲埋まっているとき、ベスト枠外の旧曲は `r ≤ r_{best30}` | 強い。ほぼ全プレイヤーで大量に得られる上限 |
| C3 | 公式レート `R` | `50·R100 ≤ Σ r（best + new） ≤ 50·R100 + 49` | 弱い。新曲枠の未知数と混ざり、幅も0.5ある |
| C4 | 公式OVER POWER | 全プレイ楽曲の楽曲OP合計が表示値と一致する | 強いが、全プレイ譜面の未知数を1本の式にまとめた制約になる |
| C5 | 登録間の差分 | 前回未プレイだった譜面が1つだけ増えたとき、OPの増分からその譜面の定数が一意に決まる | 新曲の推定に特に強い。スナップショット保存が前提（5章） |

C1・C2は、前バージョンの定数を当てはめて矛盾を探すだけでも使える。これが本設計の中心である。

### 3.2 C1・C2の具体例

S以上（900,000以上）では `r = x·10 + g(s)` と書ける（`g` はスコアだけで決まる補正値、100倍整数）。C1は

```
x_i − x_j ≥ (g(s_j) − g(s_i)) / 10
```

という定数の差の制約になる。両方が1,009,000以上なら `g` は等しいので、単に `x_i ≥ x_j` となる。

C2は、ベスト枠30位の譜面を基準にした上限になる。たとえば30位が「14.5・1,007,500（SSS）」で `r = 16.50` のとき、枠外で「14+・1,008,000」の譜面は `x + 2.05 ≤ 16.50` から定数14.4以下となり、14+と矛盾する。この場合、30位側の定数が14.6以上に上がったか、どちらかの譜面の情報が誤っている。

### 3.3 情報が得られる範囲

- 下限（C1）が付くのは、誰かのベスト枠・新曲枠に入る譜面だけである。高難度に偏り、低難度の譜面は主にC2の上限とC4だけになる。
- 推定できる範囲は利用者のレート帯の広さで決まる。レート帯ごとの採用状況は既存の `chart_best_slot_stats_by_rating_band` で概算できる。

## 4. データの選び方（重要）

### 4.1 日次バッチによる枠の上書き

`PlayerDataRecalculationBatchUsecase`（`internal/usecase/player_data_recalculation_batch.go`）は、次のプレイヤーの枠を**chunisupportの現在の定数で選び直して上書きする**。

- `last_played_at` が現行バージョン稼働日より前のプレイヤー
- 現行プレイヤーのうち、本枠が両方空、件数超過、`slot_order` 不正などで公式枠が壊れているプレイヤー

上書きされた枠を推定に使うと、自分の定数から自分の定数を推定する循環になる。また、上書きされたかどうかを後から `player_records` だけで判別する方法はない。

### 4.2 採用条件

推定には、次の条件をすべて満たす登録データだけを使う。

1. `last_played_at` が新バージョン稼働日以降である。
2. 取得日時が新バージョン稼働日以降である。
3. 公式枠の検証（件数・`slot_order` の範囲・重複）を通過している。
4. 公式レートと枠が同じ登録で取得されている。

条件1・2を満たしても、CHUNITHM-NETの枠と公式レートが新定数で再計算済みかは要検証である（7章）。

### 4.3 対象外にする譜面

- 削除済み楽曲、WORLD'S END
- `scores.standard` の解決でスキップされた譜面（マスタ不整合）
- 新曲判定は既存仕様と同じく `songs.released_at` と現行バージョン稼働日で行い、`songs.is_new` は使わない

---

## 5. データ保存の変更

現行DBは枠と公式値の最新状態だけを持つ。`player_record_histories` に枠はなく、`player_latest_updates` は差分結果だけを保存する。推定には登録時点の公式データが必要なため、登録処理で次を保存するテーブルを追加する。

| 項目 | 内容 |
|---|---|
| player_id, collected_at | 登録データの識別 |
| official_rating | 公式レート |
| official_overpower | 公式OP |
| last_played_at | 最終プレイ日時 |
| slots | 公式枠の写し（`best` / `best_candidate` / `new` / `new_candidate` の順位・chart_id・スコア・コンボランプ） |

- 日次バッチの再選出結果は保存しない。登録時の公式データだけを保存する。
- サイズを抑えるため、全スコアは保存しない。C2・C4に必要な全スコアは同時点の `player_records` と `player_record_histories` から再構成する。
- 保存期間は、新バージョン稼働後の推定期間（例: 稼働日から約2か月）に限ってよい。

## 6. 推定方法

段階的に実装する。

### 6.1 フェーズ1: 矛盾検知（ソルバー不要）

前バージョンの定数（現在の `charts.const`）を当てはめ、採用データのC1・C2の違反を数える。

- 違反ごとに、関わった2譜面と「どちらがどれだけ動けば解消するか」を記録する。
- 譜面ごとに違反件数、関わったプレイヤー数、示唆される変更方向（上げ / 下げ）を集計する。
- 多くのプレイヤーで同じ方向の違反に関わる譜面を「定数変更候補」として出力する。

単曲レーティングの切り捨てによる誤差と、同じレーティング同士の並び順の不確かさ（7章）を考慮し、差が0.01以内の違反は数えない。

Goの既存ドメインサービス（単曲レーティング計算）だけで実装でき、最初に効果を確認できる。

### 6.2 フェーズ2: 範囲の絞り込み（制約伝播）

各譜面の候補集合 `D_k`（表示レベルから決まる最大5値）を、C1・C2の制約で繰り返し絞り込む。

- 譜面iの最大値で満たせない制約があれば、譜面jの候補から外す、という操作を変化がなくなるまで繰り返す。
- 候補が1つになった譜面は「確定」、空になったら入力データに矛盾があるとして原因のプレイヤーを特定する。
- この段階では前バージョンの定数を仮定しないため、結果は厳密な範囲になる。

### 6.3 フェーズ3: 全制約による推定（CP-SAT）

C1〜C5をまとめて整数計画として解く。

- 変数: 譜面ごとの `x_k ∈ D_k`。単曲レーティングとOPは、候補5値の表引き（element制約）で表す。
- C4の楽曲OPは、難易度ごとのOPの最大値を補助変数で表す。
- 目的関数: 旧曲について「前バージョンの定数から変わった譜面数」を最小化する。
- 誤データへの対応: プレイヤーごとに「このプレイヤーの制約を外す」二値変数を置き、外した数にも罰則を与える。少数の誤データで全体が解なしになることを防ぐ。

最適解を得たあと、譜面ごとに次の2種類の範囲を求めて出力する。

| 区分 | 求め方 | 意味 |
|---|---|---|
| 厳密範囲 | 目的関数を固定せず、制約を満たす最小値・最大値 | データだけから言える範囲 |
| 推定範囲 | 目的関数を最適値に固定したうえでの最小値・最大値 | 「変更は少ない」という仮定を置いた範囲 |

譜面数分の最小化・最大化が必要になるため、フェーズ2で確定した譜面とどの制約にも現れない譜面は除いて解く。

CP-SATはGoから直接扱いにくいため、フェーズ3はAPIの外の分析ツールとし、DBからエクスポートしたデータを読んで結果をCSVで出力する構成を想定する。

### 6.4 出力

譜面ごとに次を出力する。

- 現在の定数と `is_const_unknown`
- 厳密範囲、推定範囲、推定値
- 根拠となったプレイヤー数・制約数
- フェーズ1の違反件数と変更方向

結果は管理画面または `_report` で確認し、外部の定数表やsong-batchの更新判断に使う。`charts.const` は自動更新しない。

## 7. 要検証事項

推定の正しさに直接影響するため、実装前に実データで確認する。

1. **公式枠の並び順**: CHUNITHM-NETの枠が単曲レーティング降順か。同じレーティング同士の並び順の規則（定数・スコア・曲順など）。chunisupportの `BuildRatingSlots` の並び順（[doubtful-tests.md](doubtful-tests.md) の項目1）とは別物として扱う。
2. **単曲レーティングの精度**: 公式でも単曲ごとに小数第2位で切り捨ててから合計しているか。合計後に切り捨てる場合はC3の式が変わる。
3. **公式OPの表示**: 小数第2位で切り捨てか四捨五入か。楽曲OPの切り捨て単位（0.005 / 0.05）が公式と一致するか。削除済み楽曲の記録が含まれるか。
4. **新バージョン稼働時の再計算時期**: 稼働直後のCHUNITHM-NETの枠と公式レートが、新定数で即時再計算されるか、プレイ後に再計算されるか。後者なら4.2の条件1で足りるが、前者なら未プレイのプレイヤーも使える。
5. **ベスト枠が30曲未満の場合**: 単曲レーティング0の譜面が枠に入るか。C2を適用してよい条件の確認。
6. **次点枠**: `best_candidate` の件数と並び順。順位が付いていればC1と同じ扱いにできる。

検証は、定数が確定している前バージョン末期の登録データに対して計算を当て、公式レート・公式OP・枠順と完全に一致するかで行う。一致しないプレイヤーがいれば、規則の理解か誤データのどちらかである。

---

## 8. 実装順序の案

1. 7章の検証（既存データで計算と公式値を照合）
2. 5章のスナップショット保存（次のバージョン更新より前に入れる必要がある）
3. フェーズ1の矛盾検知（Go、管理者向け出力）
4. フェーズ2の制約伝播
5. フェーズ3の分析ツール

2はバージョン更新後に入れても過去分を取り戻せないため、優先度が高い。
