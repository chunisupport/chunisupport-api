# 楽曲バッチ管理機能 設計・実装計画書

## 0. 文書の位置付け

本書は、ChuniSupportの管理画面から次の運用を行えるようにするための設計・実装計画書である。

- CHUNITHM譜面定数メインフレームのGoogleスプレッドシートIDを変更する
- `chunisupport-song-batch --major-update` 相当の大型アップデート処理を実行する
- 実行状態と結果を管理画面で確認する
- 既存cronと管理画面起点の処理を安全に共存させる

対象リポジトリは次の3つとする。

- `chunisupport-api`: 設定・ジョブの永続化、管理者API、DBマイグレーション
- `chunisupport-song-batch`: データソース取得、設定検証、大型更新、ジョブ実行
- `chunisupport-front`: 管理画面、ジョブ状態表示、確認操作

本書は実装時の基準とする。実装によりAPI仕様が確定したら、正式な仕様を各リポジトリの `docs/` とAPI仕様書へ反映する。

---

## 1. 背景と課題

### 1.1 MainframeスプレッドシートID

song-batchは `CHUNISUPPORT_BATCH_GOOGLE_SHEET_ID` で指定されたGoogleスプレッドシートから譜面定数を取得している。このスプレッドシートは大型アップデートごとに別のスプレッドシートへ切り替わるため、現在はサーバー上の環境変数を手動で変更する必要がある。

環境変数はAPIプロセスから安全に永続変更する仕組みではない。また、設定ファイルを書き換えても起動済みプロセスやcronの実行環境へ確実に反映されるとは限らない。このため、運用中に変更されるスプレッドシートIDはDB管理へ移す。

Google Cloud APIキーとGoogle Sheets APIのベースURLは運用中に管理画面から変更する値ではない。これらは引き続き環境変数で管理し、DBやAPIレスポンスへ出さない。

### 1.2 大型アップデート実行

大型アップデート時にはsong-batchを `--major-update` 付きで実行している。このモードは通常実行と異なり、公式データと追加楽曲データだけを統合対象とし、公式レベルと既存譜面定数の関係に応じて譜面定数を不明化する。

この操作には次の問題がある。

- サーバーへログインしてコマンドを実行する必要がある
- 既存cronと同時実行される可能性がある
- 実行中・成功・失敗を管理画面から確認できない
- 操作者と実行結果の監査記録が残らない
- 二重操作をAPI側で防止できない

### 1.3 現在のデータソース取得に関する安全性

現在のsong-batchは、データソースのダウンロードが一部失敗しても処理を続行する。出力先として固定の `.datasources/` を使うため、今回の取得に失敗したデータソースについて、前回実行時のJSONファイルが残っていると、その古いファイルを読み込む可能性がある。

大型アップデートで古い公式データを利用すると、意図しない不明化や更新漏れにつながる。この問題は管理画面対応の前提として解消する。

## 2. 目的

- ADMINがサーバーへログインせずにmainframeスプレッドシートを切り替えられること
- ADMINがサーバーへログインせずに大型アップデートを実行できること
- 実行枠が空いている場合、画面操作から75秒以内を目標に処理を開始すること
- 通常cron、木曜特別cron、管理画面起点の処理が同時にsong-batchの更新を行わないこと
- 取得に失敗した古いデータを誤って再利用しないこと
- 無効なスプレッドシートIDや解析不能なシートを有効化しないこと
- ジョブの要求者、状態、開始・終了時刻、結果、失敗理由を確認できること
- プロセス停止後もジョブ状態を復旧できること

---

## 3. 対象範囲

### 3.1 対象

- mainframeスプレッドシートIDのDB管理
- 新しいスプレッドシートの取得・解析・内容検証
- 検証済みスプレッドシートの有効化と譜面定数への適用
- 大型アップデートジョブの非同期実行
- DBを利用したジョブキュー
- 1分間隔で待機ジョブを取得するdispatcher
- 全song-batch実行に共通する多重起動防止
- ジョブ状態・履歴を取得する管理者API
- 管理画面の設定変更、実行、状態表示
- 障害復旧と監査ログ
- 既存CLIとcronの互換性維持

### 3.2 対象外

- Google Cloud APIキーの画面変更
- 任意の環境変数やcron式を編集する汎用管理画面
- VPS上の任意コマンド実行機能
- ジョブの実行日時予約
- 実行中ジョブの強制終了
- 一般ユーザーまたはEDITORによる実行
- `--fill-missing-release-date` の画面実行
- image-batch、stat-batchの即時実行
- cron自体の管理画面編集

プレイヤーデータ再計算と静的データ出力は、既存cronにより最終的に追随する。本機能では大型更新直後の自動実行対象に含めず、画面上に追随待ちであることを表示する。即時実行が必要になった場合は、各バッチを同じジョブ基盤へ追加する別設計として扱う。

## 4. 採用方式

### 4.1 DBジョブキューと1分dispatcher

APIはバッチプロセスを直接起動しない。APIは要求をDBへ保存し、cronから1分ごとに起動されるsong-batch dispatcherが待機ジョブを実行する。

```text
ADMIN管理画面
  │
  │ POST ジョブ要求
  ▼
chunisupport-api
  │
  │ DBへQUEUEDとして保存
  ▼
MySQL
  ▲
  │ 1分ごとに取得
  │
song-batch --run-pending-job
  ├─ 共通アドバイザリロック取得
  ├─ ジョブをRUNNINGへ遷移
  ├─ 取得・検証・統合
  └─ SUCCEEDEDまたはFAILEDへ遷移
```

目標時間は次のとおりとする。

- APIがジョブ要求を受理するまで: 通常のAPI応答時間内
- 実行枠が空いている場合の開始: 要求から75秒以内
- 他のsong-batchが実行中の場合: 既存実行の終了後、次のdispatcher起動時

75秒はcronの最大待ち時間60秒とプロセス起動・DB処理の余裕を含む。外部サービス障害や既存バッチの長時間実行中は保証対象外とし、画面には待機理由を表示する。

### 4.2 APIからの直接プロセス起動を採用しない理由

- APIの再起動やリクエストキャンセルと長時間処理の寿命を分離する必要がある
- APIプロセスへsong-batchバイナリの実行権限を与える必要がある
- 標準出力、終了コード、タイムアウト、ゾンビプロセスをAPIが管理することになる
- 複数APIインスタンス構成へ変更した場合に多重実行リスクが増える
- cron実行との排他を別途実装する必要があり、DBキューより単純にならない

### 4.3 常駐ワーカーを採用しない理由

即時性だけを優先するなら常駐ワーカーも選択肢になる。しかし、本機能の実行頻度は大型アップデート時に限られ、1分dispatcherで十分な即時性を得られる。監視対象となる常駐プロセスを増やさないため、cron起動方式を採用する。

## 5. 管理画面の仕様

### 5.1 画面構成

ADMINメニューへ「楽曲バッチ管理」を追加する。

```text
/admin/song-batch
```

画面は次の3領域で構成する。

1. 現在の実行状態
2. Mainframeデータソース管理
3. 大型アップデート実行と履歴

### 5.2 現在の実行状態

次を表示する。

- 現在実行中または待機中のジョブ
- ジョブ種別
- 要求者
- 要求日時
- 開始日時
- 現在の処理段階
- 通常cronとの競合による待機状態
- 直近の成功・失敗

状態表示中は2秒間隔で再取得し、ジョブが終了したら通常の画面再取得間隔へ戻す。ブラウザーを閉じてもサーバー側の実行は継続する。

### 5.3 Mainframeデータソース管理

次を表示する。

- 現在有効なスプレッドシートID
- `https://docs.google.com/spreadsheets/d/{id}` へのリンク
- 最終更新者
- 最終更新日時
- 直近の適用結果
- 新しいスプレッドシートIDの入力欄

入力値はスプレッドシートIDだけを受け付ける。URL全体はAPIへ送らない。IDは英数字、ハイフン、アンダースコアだけを許可し、255文字以下とする。実際に利用可能かどうかはGoogle Sheets APIからの取得結果で判断する。

「検証して適用」を押すと、確認ダイアログを表示してから非同期ジョブを登録する。この時点では現在のIDを変更しない。

### 5.4 Mainframe更新フロー

```text
新しいIDを入力
  ↓
確認ダイアログ
  ↓
MAINFRAME_SHEET_UPDATEジョブをQUEUEDで登録
  ↓
新しいIDでGoogle Sheets APIから取得
  ↓
解析結果を検証
  ├─ 失敗: 現在のIDとDBデータを変更せずFAILED
  └─ 成功
       ↓
     mainframeデータを既存楽曲・譜面へ適用
       ↓
     譜面更新と有効ID切替を同一トランザクションで確定
       ↓
     SUCCEEDED
```

設定だけを先に有効化しない。新しいmainframeデータの適用と設定変更を同一トランザクションで確定する。これにより、「設定上は新IDだがデータ適用に失敗した」という状態を作らない。

Mainframe更新ジョブはmainframeデータだけを統合する。公式データなど他のデータソースの一時障害に、スプレッドシート切替の成否を依存させない。新規楽曲がDBに存在しない場合は、その件数を未解決として結果に含める。未解決が存在する場合の扱いは以下とする。

- 未解決が0件: 適用成功
- 未解決が1件以上: DBを変更せず失敗

大型アップデート後に新シートを適用する通常の運用では、新規楽曲は先に公式データから登録済みとなるため、全件解決できることを成功条件にする。

### 5.5 Mainframe内容検証

Google APIが成功しただけでは有効化しない。次をすべて満たす必要がある。

- 取得できるシートが1枚以上ある
- 解析できる譜面が1件以上ある
- 難易度が `BAS`、`ADV`、`EXP`、`MAS`、`ULT` のいずれかである
- 定数がドメイン上の許容範囲内である
- タイトルが空でない
- 同一タイトル・同一難易度に異なる定数が存在しない
- DB上の楽曲・譜面へ全件解決できる

前回件数との比率による自動拒否は採用しない。大型アップデート直後は掲載件数が大きく変わる可能性があり、固定比率が正しい業務規則にならないためである。代わりに、総取得件数、難易度別件数、未解決件数を確認ダイアログと結果へ表示する。

### 5.6 大型アップデート実行

「大型アップデートを実行」を押した場合、確認ダイアログに次を表示する。

- 公式データと追加楽曲データだけを使用すること
- mainframe、st1027、otoge-dbは使用しないこと
- 譜面定数の不明化が行われること
- 実行中は他のsong-batchが待機またはスキップされること
- プレイヤーデータ再計算と静的データ出力は既存cronで後から追随すること
- 現在のメンテナンス状態

確認操作では固定文言 `大型アップデート` の入力を必須とする。フロントエンドの二重送信防止に加えて、APIは待機中または実行中の更新ジョブが存在する場合に新しい要求を拒否する。

大型アップデートジョブは次の順序で動作する。

1. 公式データソースと追加楽曲データソースだけを解決する
2. 両方を今回の実行専用ディレクトリへ取得する
3. 両方の取得と解析が成功したことを確認する
4. ワークスペースを構築する
5. 変更予定件数を記録する
6. MySQLの単一トランザクションで譜面データを更新する
7. ジョブ成功を同じトランザクションで記録する

公式または追加楽曲の取得・解析に失敗した場合は、DBの楽曲・譜面を一切変更しない。

### 5.7 メンテナンスモードとの関係

大型アップデート要求時にメンテナンスを自動開始・自動終了しない。

- 大型更新のDB反映は単一トランザクションで行われ、途中状態を一般利用者へ公開しない
- 自動終了すると、管理者が別目的で開始したメンテナンスを誤って解除する可能性がある
- メンテナンスコメントと終了判断は運用者の意思として維持する

管理画面には現在のメンテナンス状態とメンテナンス管理画面へのリンクを表示する。運用者は必要に応じて先にメンテナンスを開始し、大型更新と後続データの確認後に手動で終了する。

## 6. ドメインモデル

### 6.1 SongBatchConfiguration集約

運用中に変更可能なsong-batch設定を表す。

保持する値:

- `MainframeSheetID`
- `UpdatedByUserID`
- `UpdatedAt`

振る舞い:

- 検証済みIDへの切替
- 現在IDと候補IDが同じかの判定

`MainframeSheetID` は値オブジェクトとし、文字種、空文字、最大長をコンストラクタで検証する。Google APIへの接続可否は外部I/Oであり、値オブジェクトの責務に含めない。

### 6.2 SongBatchJob集約

ジョブ種別:

- `MAINFRAME_SHEET_UPDATE`
- `MAJOR_UPDATE`

ジョブ状態:

- `QUEUED`
- `RUNNING`
- `SUCCEEDED`
- `FAILED`

状態遷移:

```text
QUEUED ──開始──> RUNNING ──成功──> SUCCEEDED
                       └──失敗──> FAILED
```

`SUCCEEDED` と `FAILED` は終端状態とする。利用者による再実行は、既存ジョブの状態を戻すのではなく新しいジョブとして登録する。

集約が保証する規則:

- 終端状態から別状態へ遷移できない
- 開始時刻は `RUNNING` への遷移時に一度だけ設定する
- 終了時刻は終端状態への遷移時に一度だけ設定する
- 成功ジョブはエラーを保持しない
- 失敗ジョブは管理者向けの失敗理由を保持する
- mainframe更新ジョブだけが候補スプレッドシートIDを保持できる

## 7. DB設計

APIリポジトリへ新しいマイグレーションを追加する。既存マイグレーションは変更しない。

### 7.1 `song_batch_configurations`

単一行の設定テーブルとする。

| カラム | 型 | NULL | 内容 |
|---|---|---:|---|
| `id` | `TINYINT UNSIGNED` | NO | 常に1 |
| `mainframe_sheet_id` | `VARCHAR(255)` | YES | 現在有効なID。導入直後だけ未設定可 |
| `updated_by_user_id` | `INT UNSIGNED` | YES | 更新した内部ユーザーID |
| `updated_at` | `DATETIME(6)` | NO | UTC更新日時 |

制約:

- 主キー `id`
- `CHECK (id = 1)`
- `updated_by_user_id` は `users.id` を参照し、ユーザー削除時は `NULL`

マイグレーションで `id = 1`、`mainframe_sheet_id = NULL` の行を必ず作成する。この行は設定保存だけでなく、同時ジョブ作成を直列化するロック対象としても使用する。導入後の初回ブートストラップまたは最初のMainframe更新が成功した後は、アプリケーションのドメイン規則として `NULL` へ戻すことを禁止する。

内部ユーザーIDはJOINと監査表示のためだけに使用し、APIへ数値のまま公開しない。APIレスポンスでは更新者のユーザー名を返す。

### 7.2 `song_batch_jobs`

| カラム | 型 | NULL | 内容 |
|---|---|---:|---|
| `id` | `BINARY(16)` | NO | 外部公開用UUID |
| `type` | `VARCHAR(32)` | NO | ジョブ種別 |
| `status` | `VARCHAR(16)` | NO | ジョブ状態 |
| `requested_by_user_id` | `INT UNSIGNED` | YES | 要求者の内部ID |
| `candidate_mainframe_sheet_id` | `VARCHAR(255)` | YES | mainframe更新時の候補ID |
| `phase` | `VARCHAR(32)` | YES | 現在の処理段階 |
| `requested_at` | `DATETIME(6)` | NO | UTC要求日時 |
| `started_at` | `DATETIME(6)` | YES | UTC開始日時 |
| `finished_at` | `DATETIME(6)` | YES | UTC終了日時 |
| `lease_expires_at` | `DATETIME(6)` | YES | RUNNINGジョブの実行権期限 |
| `attempt_count` | `TINYINT UNSIGNED` | NO | 実行試行回数 |
| `result_json` | `JSON` | YES | 件数などの結果 |
| `error_code` | `VARCHAR(64)` | YES | 安定した失敗コード |
| `error_message` | `VARCHAR(1000)` | YES | 管理者向け失敗概要 |

インデックス:

- 主キー `id`
- `(status, requested_at)`
- `(requested_by_user_id, requested_at)`

`result_json` にはAPIキー、DB接続情報、外部レスポンス本文、スタックトレースを保存しない。次のような件数だけを保持する。

```json
{
  "downloaded_charts": 3200,
  "resolved_charts": 3200,
  "updated_songs": 25,
  "updated_charts": 1800,
  "unknownized_charts": 950
}
```

### 7.3 設定の初期化

移行時点ではDBに現在の環境変数値を直接埋め込めない。dispatcherまたは通常song-batchが共通ロック取得後に設定行を確認し、`mainframe_sheet_id` が `NULL` なら `CHUNISUPPORT_BATCH_GOOGLE_SHEET_ID` の値で一度だけ初期化する。

設定行が作成された後はDB値を正とし、環境変数値へフォールバックしない。環境変数は新環境のブートストラップとロールバック期間のために残せるが、通常実行時の設定変更手段としては扱わない。

## 8. API設計

すべて `/internal/admin` 配下とし、Firebase Bearer認証とADMIN権限を必須とする。レスポンスへDB数値IDを含めない。

### 8.1 状態・設定・履歴取得

```http
GET /internal/admin/song-batch
```

レスポンス例:

```json
{
  "configuration": {
    "mainframe_sheet_id": "1AbCdEf...",
    "spreadsheet_url": "https://docs.google.com/spreadsheets/d/1AbCdEf...",
    "updated_by": "admin-user",
    "updated_at": "2026-09-06T08:00:00Z"
  },
  "active_job": {
    "id": "0199...",
    "type": "MAJOR_UPDATE",
    "status": "RUNNING",
    "phase": "CONSOLIDATING",
    "requested_by": "admin-user",
    "requested_at": "2026-09-06T08:10:00Z",
    "started_at": "2026-09-06T08:10:42Z"
  },
  "recent_jobs": []
}
```

履歴は新しい順に直近20件を返す。履歴が増えても全件取得しない。

### 8.2 Mainframe更新要求

```http
POST /internal/admin/song-batch/mainframe-sheet-update-jobs
Content-Type: application/json
```

```json
{
  "sheet_id": "1AbCdEf..."
}
```

成功時は `202 Accepted` で作成したジョブを返す。

拒否条件:

- IDの形式が不正: `400 Bad Request`
- 現在有効なIDと同じ: `409 Conflict`
- 待機中または実行中の更新ジョブがある: `409 Conflict`
- 認証済みユーザーがADMINではない: `403 Forbidden`

### 8.3 大型アップデート要求

```http
POST /internal/admin/song-batch/major-update-jobs
Content-Type: application/json
```

リクエストボディは持たない。成功時は `202 Accepted` で作成したジョブを返す。

待機中または実行中の更新ジョブがある場合は `409 Conflict` とする。確認文言は誤操作を減らすためのUI仕様であり、APIの認可・排他条件として信頼しない。

### 8.4 ジョブ詳細取得

```http
GET /internal/admin/song-batch/jobs/:id
```

ジョブUUIDが不正な場合は `400 Bad Request`、存在しない場合は `404 Not Found` とする。

### 8.5 エラーコード案

- `song_batch_job_already_active`
- `song_batch_sheet_id_unchanged`
- `song_batch_sheet_unreachable`

## 9. ジョブ取得・排他・障害復旧

### 9.1 全song-batch共通ロック

通常実行、`--major-update`、`--fill-missing-release-date`、dispatcherによるジョブ実行のすべてでMySQLのアドバイザリロックを使用する。

```text
chunisupport:song-batch
```

ロックは専用DB接続で取得し、プロセス終了まで接続を保持する。

- 通常cronが取得できない場合: ログへスキップ理由を記録して終了コード0
- dispatcherが取得できない場合: ジョブをQUEUEDのままにして終了コード0
- CLIで明示実行した大型更新が取得できない場合: 実行されなかったことが分かるエラー終了

通常cronの重複回避と管理画面ジョブの排他に同じロックを使用する。モード別ロックには分けない。

### 9.2 ジョブの作成排他

APIは設定の単一行を `SELECT ... FOR UPDATE` でロックし、`QUEUED` または `RUNNING` のジョブが存在しないことを確認してから新規ジョブを保存する。これにより、複数APIリクエストが同時に到着してもアクティブな更新ジョブは1件だけになる。

### 9.3 dispatcherの取得順序

1. DB接続
2. song-batch共通アドバイザリロックを試行
3. ロック取得後、最古の `QUEUED` ジョブを `FOR UPDATE SKIP LOCKED` で取得
4. `RUNNING`、開始日時、リース期限を保存してコミット
5. ジョブ実行
6. 成功または失敗を保存
7. 共通ロックを解放

### 9.4 リースと異常終了

RUNNING遷移時にリース期限を設定し、取得、解析、統合などの処理段階ごとに延長する。プロセスが異常終了するとMySQLアドバイザリロックは接続切断により解放される。

dispatcherは期限切れRUNNINGジョブを検出した場合、次のように扱う。

- DB同期成功とジョブ成功は同一トランザクションで記録する
- 期限切れ時点でRUNNINGなら、楽曲・譜面更新はコミットされていないと判断できる
- 該当ジョブをQUEUEDへ戻して一度だけ再実行する
- 再実行でも期限切れになった場合はFAILEDにする

再試行回数は `attempt_count` に保持し、上限は2回とする。

### 9.5 成功記録の原子性

楽曲・譜面の同期と `SUCCEEDED` への遷移は同じMySQLトランザクションで行う。プロセスが同期コミット直後、成功記録前に停止して結果が不明になる状態を防ぐ。

ダウンロード、解析、SQLiteワークスペース構築はMySQLトランザクション開始前に行い、長時間トランザクションを避ける。

## 10. データソース取得の修正

### 10.1 実行専用ディレクトリ

通常のダウンロード実行では、実行ごとに一意な一時ディレクトリを作成する。正常に取得できたファイルだけをその実行の入力として扱い、処理終了後に削除する。

固定 `.datasources/` は `--skip-download` を明示した場合だけ使用する。これにより、通常実行が前回ファイルを暗黙に再利用しないようにする。

### 10.2 データソース単位の結果

Downloaderは全体のエラーだけでなく、データソースごとに次を返す。

- 成功・失敗
- 保存先
- 取得日時
- 件数またはバイト数
- 失敗理由

Importerへ渡す対象は今回の実行で取得に成功したデータソースだけとする。

### 10.3 モード別の必須条件

| モード | 必須データソース | 失敗時 |
|---|---|---|
| 通常 | なし | 成功したデータソースだけを統合 |
| 大型更新 | official、additional_songs | どちらか失敗で全体失敗 |
| Mainframe更新 | 候補mainframe | 失敗で設定・DBとも変更なし |
| `--skip-download` | CLI指定の既存ファイル | 現行の明示利用として許可 |

大型更新では、対象外データソースを解決・ダウンロードしてから除外するのではなく、最初からofficialとadditional_songsだけを対象にする。

### 10.4 Mainframe解析の重複判定

現在の重複キーに定数値が含まれる場合、同一タイトル・難易度に異なる定数があると別レコードとして残る。検証可能にするため、正規の識別キーをタイトルと難易度に変更し、異なる定数が検出された場合はエラーにする。

## 11. cron設計

既存cronは時刻を変更せず、dispatcherを1行追加する。

```cron
* * * * * cd /home/ubuntu/apps/chunisupport/songbatch && ./chunisupport-song-batch-linux-amd64 --run-pending-job
```

すべてのsong-batch起動経路が共通ロックを取得するため、既存cronとdispatcherが同時刻に起動しても更新処理は一つだけ実行される。

現在の主な競合候補は次のとおりである。

| UTC | JST | 処理 |
|---|---|---|
| 毎日19:00 | 翌日04:00 | プレイヤーデータ再計算 |
| 03:00、09:00、15:00、21:00 | 12:00、18:00、00:00、06:00 | 静的データ出力 |
| 日〜水・金・土 03:05、19:05 | 同日12:05、翌日04:05 | 通常song-batch |
| 木曜03:04、03:19 | 木曜12:04、12:19 | リリース日補完song-batch |
| 木曜04:05〜10:05 | 木曜13:05〜19:05 | 木曜毎時song-batch |
| 毎時05分 | 毎時05分 | image-batch |

本機能で直接排他するのはsong-batch同士だけとする。プレイヤーデータ再計算、静的データ出力、image-batch、stat-batchは既存のトランザクションと各バッチ固有ロックを継続利用する。

大型更新直後は次の追随遅延があり得る。

- プレイヤーデータ再計算: 次の毎日04:00 JST
- 静的データ: 次の00:00、06:00、12:00、18:00 JST
- 画像: 次の毎時05分
- 統計: 次の03:00、15:00 JST

管理画面にはこの時刻を固定文言として埋め込まず、「後続バッチは定期実行で反映」と表示する。cron変更のたびにフロントエンド修正が必要になることを避ける。

## 12. song-batch内部設計

### 12.1 CLIとユースケースの分離

`main.go` にある処理を、CLIフラグ解析から独立したアプリケーションユースケースへ移す。

概念上の入力:

```go
type RunMode string

const (
    RunModeNormal               RunMode = "NORMAL"
    RunModeMajorUpdate          RunMode = "MAJOR_UPDATE"
    RunModeMainframeSheetUpdate RunMode = "MAINFRAME_SHEET_UPDATE"
)

type RunRequest struct {
    Mode                      RunMode
    CandidateMainframeSheetID *MainframeSheetID
    JobID                     *JobID
}
```

CLIの `--major-update` とdispatcherは同じユースケースを呼び出し、処理を複製しない。

### 12.2 設定解決

データソースproviderが直接 `os.Getenv` だけを参照する構成を変更し、解決済み設定を引数で受け取る。

- APIキー、ベースURL、固定URL: 環境設定
- mainframe sheet ID: DB設定
- mainframe更新ジョブ: ジョブが保持する候補ID

Usecase層はDBモデルや環境変数名を知らず、設定providerのインターフェースだけに依存する。

### 12.3 処理段階

画面表示とログ相関のため、ジョブのphaseは次から選ぶ。

- `WAITING_FOR_LOCK`
- `DOWNLOADING`
- `VALIDATING`
- `BUILDING_WORKSPACE`
- `CONSOLIDATING`
- `FINALIZING`

QUEUEDジョブはDBロック取得前なので、原則として `WAITING_FOR_LOCK` を表示する。phaseは進捗率として扱わず、処理段階だけを表す。

## 19. 実装前に最終確認する運用判断

以下は推奨値を本書へ反映済みだが、実装開始前に運用者が最終確認する。

### 19.1 Mainframe未解決譜面

採用案: 1件でも存在すれば設定・譜面を変更せず失敗する。

理由: タイトル変更や公式データの更新漏れを見逃したまま新シートを有効化しないため。

### 19.2 メンテナンスモード

採用案: 自動開始・自動終了せず、現在状態と管理画面へのリンクだけを表示する。

理由: 別目的のメンテナンスを自動解除しないため。

### 19.3 後続バッチ

採用案: プレイヤーデータ再計算、静的データ出力、画像、統計は既存cronで追随させる。

理由: 今回の目的であるサーバーログイン不要化は達成でき、異なるバイナリを一つのジョブへ結合せずに済むため。

### 19.4 ジョブの自動再試行

採用案: 異常終了を含め最大2回。通常の入力不正や検証失敗は自動再試行しない。

理由: 恒久的なデータ不備を毎分繰り返さず、一時的なプロセス障害だけを復旧可能にするため。

## 20. 推奨する着手順

最初に `chunisupport-song-batch` の実行専用ディレクトリと共通アドバイザリロックを実装する。その後、DB・API・dispatcher・フロントエンドを一つの機能として接続する。

画面からの操作を先に作ると、現在存在する古いダウンロードファイル再利用とcron多重実行の危険を、より簡単に発生させられる状態になる。安全性基盤を先に完成させることが、本機能の実装開始条件である。
