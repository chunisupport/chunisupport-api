# フレンド機能仕様

このドキュメントは、相互承認型フレンド機能の仕様と実装方針を定義します。

## 基本方針

フレンド関係は相互承認型です。片方が申請し、相手が承認した時点でフレンド成立とします。

ユーザー検索は、ユーザー列挙を避けるため `username` の完全一致のみを許可します。存在しないユーザー、非公開ユーザー、将来のブロック状態などはレスポンス上で詳細に区別しません。

非公開ユーザーの情報は、本人または承認済みフレンドからのみ閲覧できます。フレンドから見える範囲は公開ユーザーと同じです。現時点では `friends_only` のような追加公開範囲は持ちません。

## 状態

フレンド状態はマスタデータとして管理します。マイグレーションでは `AUTO_INCREMENT` に頼らず、IDを明示指定します。

| ID | 状態 | 説明 |
| --- | --- | --- |
| 1 | `pending` | 申請中 |
| 2 | `accepted` | 承認済み |
| 3 | `blocked` | 将来利用の予約値 |

`rejected` 状態は持ちません。拒否は `pending` レコードの削除で表現します。

`blocked` は予約値です。現時点のAPIでは作成・更新しません。また、フレンド枠の上限カウントにも含めません。

## 2レコード方式

フレンド関係は片方向レコード2件で表現します。

### 申請

A が B に申請した場合、次の1件を作成します。

| user_id | friend_user_id | status |
| --- | --- | --- |
| A | B | `pending` |

### 承認

B が A からの申請を承認した場合、双方向に `accepted` を保持します。

| user_id | friend_user_id | status |
| --- | --- | --- |
| A | B | `accepted` |
| B | A | `accepted` |

### 拒否

B が A からの申請を拒否した場合、`A -> B` の `pending` レコードを削除します。

### 解除

フレンド解除はどちらからでも可能です。解除時は双方向の `accepted` レコードを削除します。

### 相互申請

A が B に申請済みの状態で B が A に申請した場合、新しい `pending` を作らず、即時に双方向 `accepted` にします。

## 上限

フレンド枠の上限は、ユーザーごとの外向き `pending` / `accepted` の合計100件です。

対象:

- `user_id = 自分`
- `status IN (pending, accepted)`

対象外:

- 自分宛ての受信申請
- 将来利用予定の `blocked`

承認時は、自分側の外向き `accepted` レコードを新規作成するため、自分の外向き件数が100件未満である必要があります。

## 非公開ユーザーの閲覧判定

対象ユーザーが非公開の場合、閲覧可能なのは次のいずれかです。

- 本人
- 承認済みフレンド

承認済みフレンド判定は、双方向に `accepted` レコードが存在することを条件にします。片方向だけ `accepted` が残っている不整合状態では、非公開情報を閲覧できません。

対象範囲:

- プロフィール
- レーティング
- レコード
- スコア履歴
- 未解禁曲
- お気に入り楽曲
- 既存の公開/非公開判定が効いている情報全般

## API

内部APIとして `/internal/friends` 配下に配置します。すべて Firebase Bearer 認証必須です。

| メソッド | パス | 説明 |
| --- | --- | --- |
| GET | `/internal/friends` | フレンド一覧 |
| POST | `/internal/friends/requests` | フレンド申請 |
| GET | `/internal/friends/requests/received` | 自分宛ての申請一覧 |
| GET | `/internal/friends/requests/sent` | 自分が送った申請一覧 |
| POST | `/internal/friends/requests/:user_id/accept` | 申請承認 |
| POST | `/internal/friends/requests/:user_id/reject` | 申請拒否 |
| DELETE | `/internal/friends/:user_id` | フレンド解除 |

申請作成だけは、ユーザーが入力する表向きIDとして `username` を使用します。

```json
{
  "username": "targetuser"
}
```

その他の操作は内部ユーザーIDをパスパラメータで指定します。

一覧レスポンスの相手ユーザー概要は次の情報を含みます。

- ユーザーID
- username
- プレイヤーレベル
- プレイヤー名
- レーティング
- 申請日時
- 承認日時

## 競合対策

外向き上限の判定とレコード作成はトランザクション内で行います。並行リクエストで100件上限を突破しないよう、自分のユーザー行をロックしてから件数確認と保存を行います。

拒否処理は `pending` 条件付き削除にします。承認処理と拒否処理が競合しても、承認済みレコードを拒否側が削除しないようにします。

非公開閲覧判定は双方向 `accepted` を要求します。片側だけ残った不整合状態をフレンド成立とは扱いません。

## DB方針

`friendship_statuses` は小規模固定マスタとして扱います。

`friendships` は片方向関係を保持します。

主な制約:

- 主キー: `(user_id, friend_user_id)`
- 自分自身への関係は禁止
- `accepted` の場合は `accepted_at` 必須
- `pending` / `blocked` の場合は `accepted_at` なし

一覧取得では相手ユーザーとプレイヤー情報をJOINしてまとめて取得し、N+1を避けます。

## 将来検討

ブロック機能は今回実装しません。将来実装時は、フレンド枠とは別枠として扱います。

実装候補:

- `blocked` を同一テーブルで扱い、上限カウントから除外する
- ブロック専用テーブルを作成する

どちらを採用する場合でも、ブロックによって通常のフレンド枠100件を消費しないことを前提にします。
