# ユーザーデータ移行仕様

## 1. 概要

ユーザーデータ移行機能は、DB内部IDが異なるChuniSupportサーバー間で、認証済みユーザー本人のプレイヤーデータを移行する機能である。

移行元と移行先では、楽曲、譜面、コース、称号、各種マスターのDB内部IDが一致しない可能性がある。このため、移行ファイルにはDB内部IDを格納せず、`official_idx`、難易度名、マスター名など、対応サーバー間で共通する外向きの値を格納する。

サーバー間の直接通信は行わない。ユーザーが移行元から署名付きJSONファイルをダウンロードし、移行先へアップロードする。

## 2. 前提条件

- 移行ファイルを相互利用するサーバーは、同じHMAC秘密鍵を安全に共有する。
- 移行先では、プレイヤーデータ、目標、目標グループ、保存済みフィルタが存在しないアカウントだけがインポートできる。
- エクスポート、検証、インポートの各ルートは機能フラグに依存せず常時登録する。ただし、メンテナンスモードでは内部API共通の利用制限を受ける。
- 移行先の既存データとのマージおよび部分インポートは行わない。
- 解決不能なマスター参照または不正なデータが1件でもある場合、データ全体をインポートしない。
- インポートは単一トランザクションで行う。
- 計算レーティングなどの派生値は、移行先のマスターデータを使用して再計算する。
- インポート成功後も、移行元のデータは自動削除しない。

HMAC署名はファイルの改変および破損を検出するためのものであり、ペイロードを暗号化しない。移行ファイルにはプレイ履歴を含む個人データが平文相当で格納されるため、ファイルの取り扱いには注意が必要である。

## 3. 移行手順

1. ユーザーが移行元サーバーへログインする。
2. エクスポートAPIから移行ファイルをダウンロードする。
3. 移行先サーバーで空のアカウントを作成し、ログインする。
4. 検証APIへ移行ファイルを送信する。
5. 返されたプレイヤー名、データ件数、インポート可否、阻害理由を確認する。
6. インポートAPIへ同じ移行ファイルを再送する。
7. インポート成功後、フロントエンドはプロフィール、レコード、履歴、目標などのユーザー関連キャッシュを破棄して再取得する。

検証結果はサーバーへ一時保存しない。インポート時には、署名、内容、マスター参照、移行先の空状態をすべて再検証する。

## 4. API仕様

すべてのエンドポイントでFirebase Bearer認証を必須とし、認証済みユーザー本人だけを対象とする。3つのAPIはユーザー単位で同じレート制限カウンターを共有し、1分間に5回まで利用できる。

### 4.1 エクスポート

```text
POST /internal/me/data-transfer/export
```

- 認証ユーザーにプレイヤーが紐付いていない場合は拒否する。
- 成功時は署名済みJSONファイルを返す。
- サーバー上に移行ファイルを保存しない。

成功レスポンスのヘッダー:

```text
Content-Type: application/json
Content-Disposition: attachment; filename="chunisupport-transfer.json"
```

### 4.2 インポート検証

```text
POST /internal/me/data-transfer/validate
```

リクエストボディには、エクスポートしたJSONファイルの内容をそのまま指定する。ファイルは永続化せず、署名、ファイル形式、スキーマバージョン、ドメイン制約、移行先のマスター参照、移行先アカウントの空状態を検証する。

レスポンス例:

```json
{
  "importable": true,
  "player_name": "TEST PLAYER",
  "counts": {
    "records": 1800,
    "record_histories": 4200,
    "worldsend_records": 40,
    "worldsend_record_histories": 80,
    "metric_histories": 20,
    "course_records": 8,
    "honors": 3,
    "favorite_songs": 25,
    "locked_songs": 12,
    "goal_groups": 3,
    "goals": 15,
    "record_filters": 4
  },
  "blockers": [],
  "unresolved_references": [],
  "unresolved_reference_count": 0
}
```

ファイル自体が不正な場合は4xxを返す。形式が正しくても移行先が空でない、またはマスター参照を解決できない場合は、`200 OK`かつ`importable: false`を返す。

| `blockers`の値 | 条件 |
|---|---|
| `destination_not_empty` | 移行先アカウントが空ではない |
| `unresolved_references` | 移行先で解決できないマスター参照がある |

`unresolved_references`は先頭100件までを返し、`unresolved_reference_count`に全件数を返す。

### 4.3 インポート

```text
POST /internal/me/data-transfer/import
```

- リクエストボディには検証時と同じ移行ファイルを指定する。
- インポート直前にすべての検証を再実行する。
- 移行先ユーザー行をロックし、空状態を再確認する。
- 移行対象を1トランザクションで保存する。
- 成功時は、新しい`player_id`とセクション別の保存件数を返す。
- 移行先が空でない場合は`409 Conflict`を返す。
- 参照解決または保存に失敗した場合は、処理全体をロールバックする。

## 5. 秘密鍵設定

APIサーバーでは次の環境変数を必須とする。settings JSONにはデータ移行用の設定項目を持たない。

```text
DATA_TRANSFER_HMAC_SECRET=<Base64で表現した32バイト以上のランダム値>
```

- Base64として厳密にデコードできる値を指定する。
- デコード後の秘密鍵は32バイト以上とする。
- 相互移行を許可するすべてのサーバーに同じ秘密鍵を設定する。
- 秘密鍵および署名値をログへ出力しない。
- バッチコマンドの実行時は秘密鍵を要求しない。
- 秘密鍵を変更すると、旧鍵で署名した移行ファイルは利用できなくなる。

## 6. 移行ファイル形式

### 6.1 エンベロープ

移行ファイルは次の3要素を持つJSONオブジェクトである。未知フィールドは拒否する。

```json
{
  "protected": "<ヘッダーJSONをBase64URL化した文字列>",
  "payload": "<ペイロードJSONをgzip圧縮してBase64URL化した文字列>",
  "signature": "<署名をBase64URL化した文字列>"
}
```

Base64URLはパディングなしの正規形式を使用する。署名対象は、ファイル内の文字列をそのまま連結した次のASCIIバイト列である。

```text
protected + "." + payload
```

署名値は次の式で生成し、定数時間比較で検証する。署名検証はgzip展開より先に行う。

```text
HMAC-SHA256(DATA_TRANSFER_HMAC_SECRET, signing_input)
```

### 6.2 保護ヘッダー

```json
{
  "format": "chunisupport-user-transfer",
  "schema_version": 2
}
```

- エクスポートではスキーマバージョン2を出力する。
- インポートではスキーマバージョン1および2を受け付ける。
- 未対応の`format`または`schema_version`は拒否する。
- サーバーID、移行ID、エクスポート日時は持たない。

スキーマバージョン2では、プレイヤー現在値および公式指標履歴に`official_overpower_percent`を追加している。スキーマバージョン1の読み込み時は、この値を`null`として扱う。

### 6.3 サイズ上限

| 対象 | 上限 |
|---|---:|
| エンベロープ全体 | 32MiB |
| Base64URLデコード後のgzipデータ | 24MiB |
| gzip解凍後のJSON | 128MiB |

データ移行ルートには32MiBのリクエストボディ上限を適用し、その他の通常ルートは5MiBの上限を維持する。gzip展開には読み込み上限を適用し、複数gzipストリームおよび上限を超える展開結果を拒否する。

## 7. ペイロード仕様

ペイロードには、移行元の`user_id`、`player_id`、楽曲ID、譜面ID、コースID、称号ID、各種マスターIDを含めない。時刻はUTCで保存する。すべての配列フィールドは必須であり、データがない場合も`null`ではなく空配列を使用する。

```json
{
  "player": {},
  "records": [],
  "record_histories": [],
  "worldsend_records": [],
  "worldsend_record_histories": [],
  "metric_histories": [],
  "course_records": [],
  "honors": [],
  "favorite_songs": [],
  "locked_songs": [],
  "goals": { "groups": [], "ungrouped": [] },
  "record_filters": []
}
```

### 7.1 プレイヤー

プレイヤー名、プレイヤーレベル、公式RATING、公式OVER POWER、公式OVER POWER割合、クラスエンブレム名、クラスエンブレムベース名、最終プレイ日時、データ取得日時、プレイヤー作成日時を移行する。公式OVER POWER割合は記録開始前のデータでは`null`となる。

計算レーティング、Best枠平均、New枠平均、計算OVER POWER値は移行せず、移行先で再計算する。`players.updated_at`および`users.updated_at`はインポート日時に更新する。

### 7.2 通常譜面レコードと履歴

現在レコードには、楽曲`official_idx`、難易度名、スコア、各ランプ名、スロット名、`slot_order`、更新日時を格納する。難易度名は`BASIC`、`ADVANCED`、`EXPERT`、`MASTER`、`ULTIMA`のいずれかである。

履歴にはスロット名と`slot_order`を除く同等の値を格納する。現在レコードと履歴は別の配列として保持し、現在値を履歴へ重複格納しない。移行先では`official_idx + 難易度名`から譜面を解決する。

### 7.3 WORLD'S ENDレコードと履歴

楽曲`official_idx`、スコア、各ランプ名、更新日時を格納する。移行先では`official_idx`からWORLD'S END譜面を解決する。

### 7.4 公式指標履歴

公式RATING、公式OVER POWER、公式OVER POWER割合、データ取得日時を格納する。公式指標はゲームから取得した値として移行元の値を維持する。

### 7.5 コース記録

コース`official_idx`、スコア、クリア状態、コンボランプ名、更新日時を格納する。コースの`display_id`および内部IDは使用しない。

### 7.6 称号

スロット番号、称号画像URL、称号名、称号タイプ名、装着日時を格納する。称号タイプは移行先に存在する必要がある。称号本体は、画像URLがある場合は画像URL、ない場合は名称と称号タイプ名で解決する。該当する称号本体が移行先に存在しない場合は、インポートトランザクション内で移行データから称号マスターを作成する。

### 7.7 お気に入り楽曲と未解禁楽曲

お気に入り楽曲には楽曲`official_idx`とお気に入り登録日時を格納する。未解禁楽曲には楽曲`official_idx`と`is_ultima`を格納する。

### 7.8 目標と目標グループ

目標グループごとに目標を入れ子にし、移行元の数値IDを参照しない。

```json
{
  "goals": {
    "groups": [
      {
        "name": "今月",
        "sort_order": 1,
        "created_at": "2026-08-01T00:00:00Z",
        "goals": []
      }
    ],
    "ungrouped": []
  }
}
```

各目標にはタイトル、achievement typeコード、`achievement_params`、`attributes`、反転指定、表示順、作成日時を格納する。`attributes`の`diff`、`genre`、`ver`は、それぞれ難易度名、ジャンル名、バージョン名へ変換して格納する。インポート時に移行先の内部IDへ戻し、既存の目標入力検証および動的上限検証を適用する。`rating_count` も移行先の最新マスタから到達可能譜面数を再計算するため、移行元と分母が異なる場合があり、0件または `count` / `remaining` 超過となる目標はインポートを拒否する。目標IDと目標グループIDは移行先で新規採番する。

### 7.9 保存済みフィルタ

保存名、`filter_type`、`schema_version`、`filter` JSONオブジェクト、作成日時、更新日時を格納する。フィルタ本文は意味解釈や変換を行わず、そのまま移行する。フィルタIDは移行先で新しいUUIDを生成する。

## 8. 移行対象外データ

| データ | 理由 |
|---|---|
| Firebase UID | 移行先アカウントの認証情報を維持するため |
| ユーザー名 | 移行先で作成したアカウント名を維持するため |
| アカウントタイプ | 移行先サーバーの権限設定を維持するため |
| 公開・非公開設定 | 移行先アカウントの設定を維持するため |
| suspicious状態 | 移行先サーバーの管理情報であるため |
| APIトークン | 認証秘密情報を持ち出さないため |
| フレンド関係 | 相手ユーザーIDがサーバー固有であるため |
| `player_latest_updates` | 通常データ登録結果のキャッシュであるため |
| 一時プレイヤーデータ | インメモリの一時処理データであるため |
| 譜面統計・ランキング集計 | サーバー全体で再集計するデータであるため |

インポート直後の`GET /internal/me/player-data/latest-update`は、次の通常データ登録まで`204 No Content`を返す。

## 9. マスター参照の変換規則

| 移行対象 | ファイル内のキー | 移行先で解決する値 |
|---|---|---|
| 通常譜面 | `song_official_idx + difficulty` | `chart_id` |
| WORLD'S END譜面 | `song_official_idx` | `worldsend_chart_id` |
| お気に入り・未解禁楽曲 | `song_official_idx` | `song_id` |
| コース | `course_official_idx` | `course_id` |
| 難易度 | 大文字の難易度名 | `difficulty_id` |
| クリアランプ | マスター名 | `clear_lamp_id` |
| コンボランプ | マスター名 | `combo_lamp_id` |
| フルチェイン | マスター名 | `full_chain_id` |
| スロット | マスター名 | `slot_id` |
| クラスエンブレム | マスター名 | `class_emblem_id` |
| クラスエンブレムベース | マスター名 | `class_emblem_base_id` |
| 称号タイプ | タイプ名 | `honor_type_id` |
| 称号 | 画像URL、または名称とタイプ名 | `honor_id` |
| achievement type | コード | `achievement_type_id` |
| 目標ジャンル条件 | ジャンル名 | `genre_id` |
| 目標バージョン条件 | バージョン名 | `version_id` |

論理削除済みの楽曲およびコースも照合対象に含める。必要な参照キーはペイロード全体から収集して種類ごとに一括取得し、レコード単位の照合によるN+1を発生させない。

## 10. 移行先の空状態

次をすべて満たす場合だけインポートできる。

1. 対象の`users`行が存在する。
2. `users.player_id IS NULL`である。
3. `players.user_id = 対象ユーザーID`の行が存在しない。
4. 目標が0件である。
5. 目標グループが0件である。
6. 保存済みフィルタが0件である。

Firebase UID、APIトークン、フレンド申請・フレンド関係、公開・非公開設定が存在していてもインポートを許可する。

検証APIでは読み取りだけで判定する。インポート時はトランザクション内で対象の`users`行を`FOR UPDATE`でロックし、同じ条件を再判定する。専用の移行済みテーブルは使用せず、インポート後はプレイヤーが紐付くため同じアカウントへの再実行を拒否する。

## 11. 検証規則

署名済みファイルであっても、次のドメイン検証を行う。署名が保証するのは発行後に内容が変更されていないことだけであり、内容の妥当性ではない。

- プレイヤー名、レベル、公式指標がドメイン制約内である。
- 通常譜面、WORLD'S END、コースの現在レコードに重複がない。
- 各履歴の譜面キーと更新日時の組み合わせに重複がない。
- DBの時刻精度へ正規化した後にも履歴キーが重複しない。
- スコア、ランプ、スロット、`slot_order`が有効である。
- Best、New、候補枠の件数と`slot_order`が既存ルールに一致する。
- 公式指標履歴が日時の昇順であり、DBの秒精度へ正規化した後の日時が重複しない。
- 称号スロットが1から3の範囲で重複しない。
- お気に入り楽曲、目標、目標グループ、保存済みフィルタが既存の件数上限以内である。
- 目標およびグループの表示順がグループごとに1から連続している。
- 目標グループ名が重複していない。
- 保存済みフィルタ本文が既存の8KiB制限を満たす。
- すべての配列が`null`ではない。

## 12. インポートと派生値

インポートでは、解決済みの譜面定数、スコア、スロット、未解禁状態から計算レーティング、Best枠平均、New枠平均、OVER POWER値を再計算する。

公式RATING、公式OVER POWER、公式OVER POWER割合、公式指標履歴は移行元の値を維持する。譜面統計およびランキングはインポート処理では更新せず、既存の集計処理で反映する。

保存は、プレイヤー、各種レコードと履歴、称号、お気に入り、未解禁楽曲、目標、保存済みフィルタ、`users.player_id`の紐付けまでを単一トランザクションで行う。一括挿入は`info.BulkInsertChunkSize`を上限に分割し、1件でも失敗した場合は全体をロールバックする。

## 13. エラー

| エラーコード | HTTP | 条件 |
|---|---:|---|
| `data_transfer_player_not_found` | 400 | エクスポート元にプレイヤーがない |
| `data_transfer_invalid_file` | 400 | JSON、Base64URL、gzip、必須項目が不正 |
| `data_transfer_invalid_signature` | 400 | HMAC署名が一致しない |
| `data_transfer_unsupported_schema` | 400 | 未対応のファイル形式またはスキーマバージョン |
| `data_transfer_invalid_data` | 400 | 値域、重複、順序、件数などが不正 |
| `data_transfer_unresolved_reference` | 400 | 移行先マスターへ解決できない |
| `data_transfer_destination_not_empty` | 409 | 移行先に対象データがある |
| `payload_too_large` | 413 | リクエストまたは圧縮前後の上限超過 |
| `internal_error` | 500 | DB、圧縮、予期しない内部不整合 |

署名値、秘密鍵、ペイロード本体、Firebase UIDをエラー本文またはログへ含めない。

## 14. アーキテクチャ

- Domain Layerは、DB IDやJSONタグを持たないユーザーデータ移行スナップショット集約と、その構造検証を担当する。
- Usecase Layerは、エクスポート、検証、インポートの調整、目標検証、阻害理由および結果の生成を担当する。
- Infra Layerは、HMAC、Base64URL、gzip、バージョン別JSON変換、スナップショット取得、マスター参照の一括解決、トランザクション保存を担当する。
- Presentation Layerは、認証ユーザーの取得、上限付きリクエスト読み込み、Usecase呼び出し、HTTPレスポンス変換を担当する。

新しいテーブルまたはカラムは使用しない。データ移行は、ユーザーに属する複数テーブルを一つの集約として取得および保存する。

## 15. 運用上の注意

- 相互移行を許可するサーバーには、対応するアプリケーションと同じHMAC秘密鍵を配備する。
- 秘密鍵のローテーションは相互移行する全サーバーで同時に行う。
- 動作確認では、内部IDが異なるサーバー間でエクスポート、検証、インポートを行い、件数、レコード、履歴、目標、フィルタ、派生値を確認する。
- 署名値、秘密鍵、ペイロード本体、Firebase UID、プレイヤー名、スコア、目標本文をログへ出力しない。
- APIの概要は`docs/API.md`、環境変数は`docs/configuration.md`、エラーコードは`docs/error_code_reason_codes.md`を参照する。
