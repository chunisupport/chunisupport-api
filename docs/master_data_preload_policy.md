# 起動時プリロード対象のマスタ整理

`migration/mysql/000001_init_schema.up.sql` に定義されているテーブルのうち、**マイグレーションで固定値が事前 INSERT されているマスタだけを**起動時にメモリへ読み込む方針に整理しました。楽曲・譜面系は件数が多く、リクエストごとの絞り込みも必要なため除外しています。

## 起動時に読み込む
| テーブル | 理由 |
| --- | --- |
| `genres` | 7件のみの楽曲ジャンルマスタで固定値。表示順は `sort_order` で管理する。 |
| `difficulties` | 5件のみの難易度マスタで固定値。 |
| `class_emblems` / `class_emblem_bases` | クラスエンブレム種別で件数少、定義済みマスタ。 |
| `clear_lamp_types` / `combo_lamp_types` | クリア・コンボランプ種別で件数少、定義済みマスタ。 |
| `slots` | 称号スロット種別、5件の固定マスタ。 |
| `full_chain_types` | フルチェインランプ種別、3件の固定マスタ。 |
| `honor_types` | 称号の種類マスタで固定値が事前投入されている。 |
| `account_types` | ユーザー権限区分。4件の固定マスタ（PLAYER/EDITOR/ADMIN/EXTDEV）。 |
| `versions` | CHUNITHMバージョン名マスタ。未来版を含む全件を読み込み、公開ビューでは読取時点で稼働開始済み（稼働日の日本時間7:00以降。[日付の切り替わり](chunithm_specs/date_boundary.md)）の行だけを返す。管理APIの書込成功後はホットリロードする。 |
| `achievement_types` | 目標機能の成果種別マスタ（11件の固定値）。`goals.achievement_type_id` の外部キー参照元で、実体は `code` 列の固定値です。 |

## 読み込まない（随時参照）
| テーブル | 理由 |
| --- | --- |
| `honors` | 初期 INSERT が無く件数増加が想定されるため、プリロードせず必要時に参照する。 |
| `songs` | 楽曲の基本情報。起動時プリロードの対象外。未プレイ補完と `updated-at` は[楽曲カタログキャッシュ](#楽曲カタログキャッシュ)から参照し、それ以外はオンデマンドで取得。 |
| `charts` | 譜面情報。`songs` と同じ。 |
| `worldsend_charts` | WORLD'S END譜面情報。`songs` と同じ。 |
| `course_classes` | 7種類の固定マスタだが、コースリポジトリが都度参照する。 |
| `courses` | `song_batch`の直接DB更新を再起動なしで反映するため、必要なidxだけを随時参照する。 |
| `users` / `players` / `player_honors` | ユーザーやプレイヤープロフィールの動的データで更新が入るためキャッシュしない。 |
| `api_tokens` | 認証系の動的データで更新が入るため除外。 |
| `player_records` / `player_worldsend_records` / `player_course_records` | スコア記録。更新頻度が高く件数も多いためプリロードしない。 |

## 補足
- `versions` は管理用の全件ビューと公開用のリリース済みビューを持ちます。管理APIによる追加・改名・削除は再起動なしで両ビューへ反映され、未来版は稼働日の日本時間7:00から公開ビューへ現れます。0:00ではありません。
- APIは単一プロセスで運用します。`versions` の書込直列化、バージョン削除と楽曲書込の排他、ホットリロードは同一プロセス内で保証します。
- `versions` 以外のプリロード対象をDBで変更した場合は、引き続き再起動が必要です。

## 楽曲カタログキャッシュ

楽曲・譜面は参照頻度に対して更新頻度が低いため、APIプロセス内で共有するメモリキャッシュ（楽曲カタログ）を持ちます。DBを正とし、キャッシュは参照用の写しです。起動時プリロードのマスタとは異なり、APIの再起動なしで変更を反映します。

### 対象と利用箇所

- 対象は通常楽曲・通常譜面・WORLD'S END楽曲・WORLD'S END譜面（削除済みを含む）と、それらの `updated_at` の最大値です。ユーザーの成績や統計データは対象外です。
- 現在の利用箇所は次のとおりです。
  - ユーザーレコード（プロフィール・レコード一覧）の未プレイ譜面補完。通常譜面と WORLD'S END の両方で、削除済み楽曲を除き、返却内容と並び順（楽曲ID順、難易度順）は従来どおりです。
  - `GET /internal/songs/updated-at`。
- 楽曲一覧・互換マスタAPIなどは現時点ではDBから取得します。適用する場合も、同じ `SongCatalogProvider` を使い、利用箇所ごとに独立したキャッシュを持たせません。
- 編集者向けの単曲取得・一覧、編集時の存在確認・検証・更新競合の判定は、古いキャッシュを正としないためDBを参照します。

### 世代と整合性

- 楽曲・譜面を変更するトランザクションは、同じトランザクション内で `song_catalog_revision.revision` を1つ進めます。APIのリポジトリ（楽曲・WORLD'S ENDの追加・保存・一括更新）と song-batch の MySQL 同期が対象です。`MAX(updated_at)` は秒精度で、同じ秒の変更やコミットの遅いトランザクションを取りこぼすため、変更検知には使いません。
- 再構築は読み取り専用の REPEATABLE READ トランザクション内で、世代番号・楽曲・譜面・`updated_at` の最大値を同じ時点から読み取ります。コミット前の変更は公開しません。
- 全件を構築し終えてから、楽曲データと更新時刻をまとめて1回で差し替えます。構築途中のデータは公開されず、`updated-at` だけが新しい世代へ先行することもありません。
- キャッシュは取得のたびに楽曲・譜面を複製して返します。利用側が値を変更しても共有データは汚染されません。

### 反映タイミング

| 変更経路 | 反映タイミング | 許容する反映遅延 |
| --- | --- | --- |
| API の楽曲・WORLD'S END 編集（追加・編集・一括編集・削除・復活・定数更新） | DBコミット後、応答を返す前に同期的に再構築します。一括編集も保存1回につき再構築1回です。 | なし（応答時点で反映済み）。再構築に失敗した場合のみ、次の世代確認まで |
| 管理画面からの song-batch | ジョブ成功後に同期的に再構築します。 | なし |
| CLI の song-batch（別プロセス） | APIが `song_catalog_revision` を10秒ごとに確認し、変化していれば再構築します。 | 最大10秒＋再構築時間（実データ相当で約40ms） |
| SQL による直接変更 | 世代を進めた場合のみ、CLI と同じく次の確認で反映します。 | 世代を進めない変更は反映されません |

確認間隔は `info.SongCatalogRevisionPollInterval`、保存後の同期再構築の上限時間は `info.SongCatalogRefreshTimeout`（30秒）です。世代確認は主キー1行の取得だけで、変化がなければ再構築しません。

### 失敗時の動作

- **初回構築**: サーバー起動直後にバックグラウンドで構築します。失敗しても起動は継続し、カタログを使うリクエストは構築を再試行し、失敗した場合は500を返します。以後も確認周期ごとに再試行します。
- **再構築の失敗**: 公開中の世代を維持してERRORログを出し、次の確認周期で再試行します。
- **DB保存成功後の再構築失敗**: 保存はコミット済みのため、編集APIは成功を返します。ERRORログを出し、次の確認周期で反映します。それまでの間、未プレイ補完と `updated-at` は保存前の世代を返しますが、編集者が保存結果を確認する単曲取得・一覧はDBから取得するため、保存結果を誤認しません。

### 同時実行

- 参照はロックを取らず、公開中の世代をアトミックに読み取るだけです。再構築中も旧世代を返します。
- 再構築は直列化し、待機後に世代が最新なら省略します。同時に複数の保存や世代確認が重なっても、同じ世代を重複して構築しません。
- 世代の更新は行ロックを取るため、楽曲・譜面の書き込みトランザクションはコミットまで直列化されます。編集・バッチとも頻度が低いため許容します。

### 計測結果

通常楽曲1,500曲（うちULTIMAあり150曲、譜面6,150件）、WORLD'S END 700曲の実データ相当の件数で、MySQL 8.4（Docker、4 vCPU）を使って計測しました。再計測は次のコマンドで行えます。

```bash
TEST_MYSQL_DSN='root:<password>@tcp(127.0.0.1:3306)/' go test -run '^$' -bench 'SongCatalog|UnplayedCompletionSource|SongsUpdatedAt' -benchtime=30x ./internal/infra/repository/
```

| 項目 | 結果 |
| --- | --- |
| 保持メモリ量 | 約1.9 MiB |
| 全件再構築（1回） | 約40ms、SELECT 5回、総確保量 約8.7 MiB（26.6万回） |
| 旧世代を保持したまま再構築したときのピーク（上限値） | 約10.6 MiB |

| 対象 | DBクエリ数 | 処理時間 | メモリ確保量 |
| --- | --- | --- | --- |
| 未プレイ補完の楽曲・譜面取得（改善前: DB全件取得） | 3回 | 約30〜43ms | 約7.3 MiB（21.9万回） |
| 未プレイ補完の楽曲・譜面取得（改善後: キャッシュから複製） | 0回 | 約1.5〜2ms | 約1.5 MiB（4.6万回） |
| `updated-at`（改善前: DB問い合わせ） | 1回 | 約2ms | 632 B |
| `updated-at`（改善後: メモリ） | 0回 | 約0.3µs | 0 B |

未プレイ補完の改善後の確保量は、共有データを汚染させないための複製によるものです。

## 統計データ

統計データはアプリケーション本体と同じMySQLデータベースに保存されます。

### 統計用テーブル

| テーブル | 説明 |
| --- | --- |
| `rating_bands` | レーティング帯マスタ（ID 0〜29 の30件。ALL含む固定値）。起動時にメモリへ読み込まれます。 |
| `chart_stats_by_rating_band` | 譜面×レーティング帯別の統計データ。定期バッチで更新され、リクエスト時に参照されます。 |
| `worldsend_chart_stats_by_rating_band` | WORLD'S END譜面×レーティング帯別の統計データ。定期バッチで更新され、リクエスト時に参照されます。 |
| `chart_best_slot_stats_by_rating_band` | 通常譜面×レーティング帯別のベスト枠採用統計。定期バッチで更新されます。 |

`rating_bands`は起動時にプリロードし、統計3表はリクエスト時に参照します。
