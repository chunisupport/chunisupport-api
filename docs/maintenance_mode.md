# メンテナンスモード仕様

## 1. 文書の位置付け

本書は、chunisupport API のメンテナンスモードについて、利用者およびAPIクライアントから観測できる振る舞いと運用上の規則を定義する。

実装方式、内部アーキテクチャ、ソースコードの配置、データの保存方式、デプロイ手順は本書の対象外とする。各エンドポイントの詳細なHTTP入出力は [API仕様書](API.md) を参照すること。

## 2. 目的と対象範囲

メンテナンスモードの目的は、計画作業中の一般利用を一時的に停止しながら、運用担当者による確認と復旧操作を継続できるようにすることである。

本書の対象:

- APIの運用状態と状態遷移
- メンテナンス中のアクセス制御
- 公開用メンテナンスコメント
- 状態確認、状態変更、遮断時の外部契約
- 死活チェックとメンテナンス状態の区別

本書の対象外:

- フロントエンドのメンテナンス画面や管理画面
- リバースプロキシなど、API以外のコンポーネントが返す代替応答
- API停止、ネットワーク障害、依存サービス障害の検知
- 開始日時または終了日時の予約
- 読み取り専用モード
- デプロイ処理との自動連携

## 3. 状態と状態遷移

APIの運用状態は次の2種類とする。

| 状態 | 公開値 | 意味 | 公開用コメント |
| --- | --- | --- | --- |
| 通常運用 | `operational` | 通常どおり各エンドポイントを提供する | 空文字 |
| メンテナンス中 | `maintenance` | 本書で定める利用者だけにアクセスを許可する | 1文字以上 |

状態には最終更新日時が付随し、RFC 3339形式で公開する。保存済みの状態はAPIの再起動後も維持し、再起動だけを理由にメンテナンスを終了してはならない。

状態変更はADMINだけが行える。

| 操作 | 指定 | 結果 |
| --- | --- | --- |
| 開始 | `enabled: true` と有効なコメント | `maintenance` へ変更する |
| コメント更新 | メンテナンス中に `enabled: true` と新しいコメント | 状態を維持してコメントを更新する |
| 終了 | `enabled: false` | `operational` へ変更し、コメントを空にする |

指定内容にコメントの正規化と状態遷移の規則を適用した結果が現在の状態と同じ場合はno-opとし、最終更新日時も変更しない。したがって、通常運用中に `enabled: false` とコメントを指定した場合も、コメントを空文字として扱った結果に変更がなければno-opとなる。

## 4. メンテナンスコメント

メンテナンスコメントは、利用者へ作業状況を知らせるためのプレーンテキストとする。

- 改行を許可する。
- 最大長は1,000 Unicodeコードポイントとする。
- `CRLF` と `CR` は `LF` に正規化する。
- 前後の空白は除去する。
- `LF` 以外の制御文字は許可しない。
- メンテナンス開始時およびコメント更新時は、正規化後の空文字を許可しない。
- メンテナンス終了時は、リクエスト内容にかかわらずコメントを空文字にする。
- HTMLとして解釈せず、クライアントでもテキストとして表示する。

メンテナンスによる個々の遮断応答にはコメントを含めない。表示が必要なクライアントは、公開状態確認APIから取得する。

## 5. アクセス制御

通常運用中は、各エンドポイントに既存の認証・認可規則を適用する。メンテナンス中は、例外経路を除き次の規則を追加で適用する。

| 利用者 | 通常のエンドポイント | 状態変更 |
| --- | --- | --- |
| ADMIN | 利用可 | 利用可 |
| EDITOR | 利用可 | 不可 |
| PLAYER | `503 Service Unavailable` | 不可 |
| EXTDEV | `503 Service Unavailable` | 不可 |
| 未認証または不正な認証情報 | `503 Service Unavailable` | 不可 |

ADMINまたはEDITORとしてメンテナンス中のアクセスを許可された場合も、対象エンドポイントが本来要求する認証・認可は省略しない。例えば、ADMIN専用エンドポイントをEDITORが利用することはできない。

スタッフ判定に使用する認証方式は、APIの既存契約に従う。

- `/internal` および `/`: Firebase IDトークン
- `/v1`、`/compat` および `/version`: APIトークン

## 6. 例外経路

次のリクエストは、メンテナンス中も一般利用者を一律に遮断しない。

- すべての `OPTIONS` リクエスト
- `GET /healthz`
- `GET /internal/system/status`
- `POST /internal/auth/login`

未登録のパスは、メンテナンス中も `404 Not Found` を返す。`POST /internal/auth/signup` は例外ではなく、メンテナンス中はスタッフ以外に `503 Service Unavailable` を返す。

### ログイン

ログインでは、メンテナンス中も通常のレート制限、Turnstile検証、Firebase認証を行う。

- 認証に成功したADMINまたはEDITORはログインできる。
- 認証に成功したPLAYERまたはEXTDEVには `503 Service Unavailable` を返す。
- Turnstile検証またはFirebase認証に失敗した場合は、メンテナンス状態にかかわらず通常の認証エラーを返す。

## 7. 公開状態確認

```http
GET /internal/system/status
```

- 認証は不要とする。
- 通常運用中とメンテナンス中のどちらでも `200 OK` を返す。
- キャッシュによる状態の取り違えを防ぐため、`Cache-Control: no-store` を返す。
- 運用状態、公開用コメント、最終更新日時を返す。
- 通常運用中のコメントは空文字とする。
- 更新者を識別する内部情報は公開しない。

## 8. 状態変更

```http
PUT /internal/admin/maintenance
```

Firebase IDトークンによる認証を必須とし、ADMINだけが実行できる。EDITORを含むADMIN以外の認証済み利用者には `403 Forbidden` を返す。

- `enabled` は必須とする。
- `enabled: true` はメンテナンスの開始またはコメント更新を表す。
- `enabled: false` はメンテナンスの終了を表し、コメントを空にする。
- 成功時は `200 OK` とし、公開状態確認APIと同じ状態を返す。
- 成功時のレスポンスには `Cache-Control: no-store` を付与する。

主なエラー:

- `400 Bad Request`: JSON、`enabled`、または `enabled: true` のときのコメントが不正
- `401 Unauthorized`: 通常運用中のFirebase認証失敗
- `403 Forbidden`: ADMIN以外による状態変更
- `503 Service Unavailable`: メンテナンス中のスタッフ以外によるアクセス

## 9. 遮断時の応答

### 標準API

互換API以外では `503 Service Unavailable` と専用エラーコード `maintenance_mode` を返す。`maintenance_mode` はメンテナンスによる利用制限を示し、その他の一時的なサービス障害とは区別する。

- `Retry-After: 60` を返す。
- `Cache-Control: no-store` を返す。
- メンテナンスコメントは含めない。
- 許可されたオリジンからブラウザで待機時間を参照できるよう、`Retry-After` はCORSの公開レスポンスヘッダーに含める。

### 互換API

`/compat/chunirec/2.0` と `/compat/reiwa/1` は、既存クライアントとの互換性を維持するため、文字列の `maintenance_mode` ではなく数値のエラーコード `503` を含む既存の互換形式を返す。`Retry-After: 60` と `Cache-Control: no-store` は標準APIと同様に付与する。

各エンドポイントのリクエスト・レスポンス形式とエラー本文の詳細は、[API仕様書](API.md) を参照すること。

## 10. 死活チェック

`GET /healthz` はAPIプロセスの死活確認を目的とし、メンテナンス中も `204 No Content` を返す。

メンテナンスはAPIプロセスの異常を意味しない。利用者向けの運用状態は `GET /internal/system/status`、プロセスの生存は `GET /healthz` で確認する。
